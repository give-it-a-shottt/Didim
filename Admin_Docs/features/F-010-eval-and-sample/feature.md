## 설계 의도 (사용자 확인 — 코드 작성 전에 채움, 문장 정리사 사용)
- 이 기능이 해결하는 문제 (사용자 확인 2026-11-17):
  1. 평가 결과가 기능별 JSON · 판정지에 흩어져 있어서 한 곳에서 볼 수 없다.
  2. 평가 데이터가 공고 6개 · 노트 10개 정도라 수치를 믿기 어렵다.
  3. 기록이 없는 첫 방문자(면접관 포함)는 이 서비스가 무엇을 하는지 볼 수 없다.
  4. 평가 스크립트를 기능마다 따로 돌려야 해서, 모델이나 프롬프트를 바꾼 뒤 회차끼리 비교하기 어렵다.
- 완료 기준 (사용자 확인 2026-11-17):
  1. 평가 데이터가 D-005 규모로 늘어나 있다. 가상 공고 10개와 카드용 노트 20개를 쓰고, 정답은 글을 쓰기 전에 먼저 정한다.
  2. 명령 하나로 기능별 평가를 돌릴 수 있고, 회차마다 요약 파일(모델 · 날짜 · 수치)이 남는다.
  3. 평가 리포트 화면(SET_02_001)에서 기능별 수치와 회차 비교를 볼 수 있고, README 표도 같은 수치를 보여 준다.
  4. 샘플 체험(DEM_01_001)에서 샘플 계정의 평가 데이터를 읽기 전용으로 둘러볼 수 있다.
- 화면 · 컴포넌트 (사용자 확인 2026-11-17 → D-029):
  - 샘플 체험(DEM_01_001): [샘플로 체험하기]를 누르면 샘플 사용자로 들어가서 기존 화면(기록 · 카드 · 공고 · 자소서 · 면접)을 그대로 둘러본다.
    - 화면에는 '샘플' 배지와 [체험 끝내기]를 보여 준다.
    - 쓰기와 AI 호출은 서버가 막는다.
    - `/demo`는 체험으로 들어가는 입구(안내 한 장)다.
    - 로그인 없이 볼 수 있고, 샘플 화면은 검색에 노출하지 않는다(noindex).
  - 평가 리포트(SET_02_001): 로그인 없이 보는 공개 페이지로 옮기고 검색에 노출한다. 주소는 `/report`다.
- API (사용자 확인 2026-11-17):
  - `POST /api/demo/session` (로그인 없이): 샘플 사용자 세션 쿠키를 발급한다. 같은 쿠키를 바꿔 끼우기 때문에, 로그인한 사람이 체험하면 로그아웃된다. 버튼 옆에 이 점을 미리 알린다. [체험 끝내기]는 로그아웃한 뒤 랜딩으로 간다.
  - 샘플 막기는 미들웨어 한 곳에서 한다. 샘플 세션이 `GET`이 아닌 요청을 보내면 403을 돌려준다. 허용하는 것은 `/logout` 하나다. 노션 `/connect` · `/callback`은 `GET`이지만 막는 목록에 넣는다. 기본값이 '막기'라서, 새 API를 만들 때 깜빡해도 새지 않는다.
  - `GET /api/report` (로그인 없이): 한 번에 돌리기가 `backend/eval/summary/`에 남긴 회차별 요약 JSON을 읽어서 돌려준다. README 표도 같은 파일로 만든다. DB는 바꾸지 않는다.
- 데이터 (사용자 확인 2026-11-17):
  - 샘플 사용자 알아보기: 샘플 사용자의 `google_sub`를 예약값 `didim-sample`로 둔다. 마이그레이션은 하지 않는다(D-025).
  - 샘플 데이터 넣기: 시드 스크립트가 리포트에 쓴 평가 회차의 결과(노트 · 카드 · 공고 · 매칭 · 퀴즈 · 초안 · 면접 질문)를 샘플 계정에 그대로 저장한다. 시드할 때는 AI를 호출하지 않는다. 다시 돌리면 샘플 데이터를 지우고 새로 넣는다. 그래서 리포트 수치와 샘플 화면이 같은 데이터를 보여 준다(D-005).
  - 평가 데이터 늘리기: 경험을 12개에서 20개로(가상 노트 추가), 공고를 6개에서 10개로 늘리고, 자소서 문항을 공고 4개분 더한다. 정답을 먼저 정하고 글을 쓴다. 퀴즈 노트 10개는 그대로 둔다.
  - 한 번에 돌리기: 가상 데이터로 하는 평가 5개(퀴즈 · 카드 · 매칭 · 자소서 · 면접)를 묶는다. 검색 평가는 내 실제 기록이라 빼고, README에 '참고 사례'로만 적는다.
- 미리 정한 것 (사용자 선택 2026-11-13): 평가 데이터는 개발 직무 공고만(Q-007). 샘플 체험 데이터는 샘플 전용 계정 하나에 둔다(Q-004 → D-025).
