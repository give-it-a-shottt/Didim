## 지적
- [제안] [확실] 전체 시간 상한에 걸릴 때 진행 중이던 `chat()` 안의 연결 재시도가 사라져 usage.calls가 실제보다 1 적다. 마감 분기는 "끝난 호출 + 진행 중 1번"으로 세지만, 진행 중인 chat이 이미 첫 HTTP 요청에 실패(503 · 타임아웃 등)하고 두 번째 요청 중이었다면 실제 HTTP 요청은 2번이다. 스크래치 스크립트에서 503 → 응답 지연 서버로 deadline 0.2초를 걸어 실제 요청 2번, 보고 usage.calls 1을 확인. 타임아웃 재시도는 서버가 이미 과금했을 수 있어 "적게 세지 않는다"(base.py:32)는 약속과 어긋난다. 바깥에서 작업이 취소(CancelledError)되면 그때까지의 usage는 아예 전달되지 않는데, 이는 FastAPI가 요청 처리를 취소하는 경우에만 생기므로 [추정]으로 함께 적는다(첫 사용 기능의 라우터 · 미들웨어 구성을 보면 확정). — 위치: backend/app/llm/structured.py:176-180, backend/app/llm/openai_compat.py:109-124 — 확인한 범위: 패킷 코드 + 스크래치 스크립트로 레포 코드를 불러 MockTransport 측정(레포 파일 수정 없음) — 고치는 방법: 가장 간단히는 마감 분기에서 진행 중 호출을 `LLMUsage(calls=LLM_MAX_TRANSIENT_ATTEMPTS)`로 세어 많게 세는 쪽으로 맞추고, 정확히 하려면 complete_json이 가진 카운터를 chat에 넘겨 HTTP 요청을 보내기 직전에 calls를 올린다(이러면 바깥 취소 때도 부른 쪽이 그 카운터로 셀 수 있음).
