## 지적
- [신규] [제안] [확실] 노트 번호 · 조각 번호의 "32비트 위쪽 경계"가 화면 테스트에서 실행되지 않는다. `parseDbId`는 `^[1-9]\d{0,9}$`를 통과한 뒤 `id <= MAX_DB_ID`로 한 번 더 거르는데(10자리인데 2,147,483,647보다 큰 값, 예: 2147483648), Playwright는 11자리(99999999999)만 넣어서 정규식 단계에서 걸린다. 그래서 `id <= MAX_DB_ID` 분기가 깨져도(예: 상한을 빼도) 테스트가 모두 통과한다. 이 분기가 없으면 2147483648이 백엔드로 넘어가 404로 끝나므로 화면에는 같아 보이지만, 1차 리뷰 E에서 "DB에 묻기 전에 거른다"고 정한 동작이 확인되지 않는다. `?chunk=abc`(숫자 아님) 경로도 테스트가 없다(코드는 null로 처리해 강조 없이 원문). 백엔드 쪽은 MAX_NOTE_ID+1과 10**20이 모두 테스트된다 — frontend/src/app/(app)/records/[noteId]/page.tsx:14-22 · frontend/tests/record-search.spec.ts:77("이상한 주소" 테스트) — 확인한 범위: page.tsx의 parseDbId 전체 + record-search.spec.ts 전체 + backend/tests/test_search.py의 범위 밖 테스트 — 고치는 방법: "이상한 주소" 테스트의 경로 목록에 `/records/2147483648`을 한 줄 추가하고, `/records/1?chunk=abc`가 강조 없이 원문만 보이는지 한 줄 추가한다(`/records/1?chunk=999`와 같은 확인). 비용이 작다.

## 체크 항목별 근거
- 프론트 로딩 상태 → records/page.tsx Suspense fallback `role="status"`와 `key={query}`가 그대로이고 이번에 바뀐 곳 없음 → 처리함
- 프론트 에러 상태 → 1차 주의 2 해결. 모의 서버에 "검색오류"(500) · "모양틀림"(200인데 모양 틀림) · 노트 500을 추가했고 spec이 "검색하지 못했어요" · "노트를 불러오지 못했어요"를 확인함(record-search.spec.ts "서버 오류나 모양이 틀린 응답…"). 503은 서버 문구(검색불가 · 시간초과)를 그대로 보여 주는 것까지 확인함 → 처리함 · 테스트됨
- 프론트 빈 데이터 상태 → "없는말" 결과 0개 문구 테스트 유지, `?chunk=999`(없는 조각)는 강조 없이 원문 테스트 추가(1차 제안 5의 일부 해결) → 처리함 · 테스트됨
- 프론트 네트워크 실패 → `fetchBackendAsUser`가 fetch 예외를 null로 바꾸고 호출부가 null을 error로 다룸(backend.ts:15-25). 연결 자체가 끊기는 경우를 흉내 내는 테스트는 없으나, 같은 error 상태를 500 · 모양 틀림 테스트가 이미 실행하므로 지적하지 않음. auth.ts도 같은 함수를 쓰며 동작(null → 비로그인)은 그대로 → 처리함
- 프론트 입력 오류 메시지 → 검색어 maxLength · 공백뿐이면 검색 안 함 유지. `/records/abc` · `/records/0` · 11자리 · `?chunk=999` 테스트가 추가됨(1차 제안 5 대부분 해결). 남은 경계는 위 지적 1건. 401 구분은 사용자 판정(F)이라 다시 지적하지 않음
- 백엔드 응답 코드 → 시간 상한 초과를 503 + `TIMEOUT_DETAIL`로 따로 답함(search.py:176-177, 테스트: 가짜 방식으로 503 · 문구 · 로그 0건). 노트 번호 범위 밖은 DB에 묻기 전에 404(notes.py:87-88, 테스트 0 · -1 · 2^31 · 10^20). `limit=0` 422 테스트 추가(1차 제안 해결). 시간 초과가 아닌 DB 오류는 여전히 500이며 사용자 판정(I, Q-012)이라 다시 지적하지 않음
- 백엔드 트랜잭션 롤백 → 1차 주의 1 해결. `test_results_are_still_returned_when_saving_the_log_fails`가 commit 실패 → rollback 1번 · 200 · 결과 그대로 · 로그 0건 · 실패 로그에 검색어 없음을 확인함. 시간 초과 시 `db.rollback()` 뒤 세션 재사용 · 설정이 트랜잭션 끝에 원래대로 돌아오는 것도 PostgreSQL 테스트로 확인함(pg_sleep(1)을 50ms에서 멈춤). `OperationalError`가 아닌 다른 DB 오류 때는 rollback 없이 다시 던지지만 요청이 끝나며 세션이 닫히므로 문제 없음 → 코드 맞음 · 테스트됨
