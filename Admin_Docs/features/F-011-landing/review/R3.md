## 체크 항목별 근거
- 모양 검사가 진짜 응답을 잘못 거절하는가 → response_model이 모든 칸을 항상 내보냄. null 가능 칸은 isStringOrNull이 허용, value는 null 또는 number, labels_pending · data 값은 항상 number, JSON에는 NaN · Infinity가 실리지 않음(`Number.isFinite`는 방어일 뿐). 실제 `read_report()` 결과 true, `{runs:[]}` true(패킷) → 잘못 거절할 경우를 찾지 못함, 통과.
- 스위치를 같이 쓰는 테스트가 한 워커에서 차례로 도는가 → config는 `fullyParallel: true` · `retries: 0`, 파일 맨 위 `test.describe.configure({ mode: "default" })`가 이 파일 안에서 fullyParallel을 덮어써 선언 순서대로 한 워커에서 돈다(실패하면 워커가 새로 떠도 다음 테스트는 계속, 각 테스트가 mode를 먼저 정함). 8101 · report-mode를 쓰는 파일은 grep으로 이 파일 하나 → 통과.
- 스위치 상태가 다른 테스트로 새는가 → 스위치는 8101 프로세스 안에만 있고 메인 mock은 안 건드림. 요청 수는 `>` 비교라 누적에도 안전 → 통과(제안 3 참고).
- 프론트 로딩 · 에러 · 빈 데이터 → getReportRuns는 연결 실패 · 비정상 상태 · JSON 아님 · 모양 틀림을 모두 null로, ReportBody는 null이면 `role="alert"`, 빈 배열이면 `role="status"`, 랜딩은 수치 칸만 숨김 → 통과.
- 외부 API 실패 대응 → 모양 검사가 더해져 서버 렌더 중 TypeError 경로가 닫힘 → 통과.
- 테스트 정상 · 예외 포함과 통과 → 500 · JSON 아님 · 모양 틀림 · 회차 0개를 랜딩 · 리포트 양쪽에서. bad-run은 고치기 전 2개 실패 → 고친 뒤 통과라 회귀 테스트 구실을 함. tsc · eslint · Playwright 121 passed → 통과(안쪽 단계는 제안 1).
