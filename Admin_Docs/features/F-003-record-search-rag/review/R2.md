## 지적

(보안 [위험] 없음. 보안 · 성능 순서로 적었다.)

- [주의] [확실] 검색 한 번에 드는 시간과 검색 횟수에 상한이 없다. 패킷 실측(사용자당 조각 1만 개)에서 낱말 1개 3.3초, 낱말 4개 6.4초가 걸렸는데, 낱말은 10개까지 받는다(config.py:38 `MAX_SEARCH_TERMS`). 비용은 "맞는 행 수 × 낱말 수"에 비례해 늘어난다. 그런데 DB 쪽 statement_timeout이 없다(session.py:26-33의 connect_args는 connect_timeout만 있음). 사용자별 검색 횟수 상한과 사용자별 조각 총량 상한도 없다. 검색 API는 동기 함수(api/search.py:44)라서, 도는 동안 스레드 하나와 DB 연결 하나를 붙잡는다. 엔진은 SQLAlchemy 기본 풀(5개 + 넘침 10개, 대기 30초)을 쓴다. 그래서 무거운 검색이 동시에 15개를 넘으면 로그인 · 가져오기 같은 다른 요청이 연결을 기다리다 실패할 수 있다. 계정 하나가 큰 기록을 올린 뒤 검색을 되풀이하면 다른 사용자도 느려진다. 검색마다 search_logs에 1행씩 쌓이는 것도 같은 상한이 없다.
  행마다 비용이 큰 이유가 있다. 낱말마다 SELECT의 CASE가 `content %> 낱말`과 `word_similarity(낱말, content)`를 따로 계산한다. PostgreSQL(psycopg) 방언으로 컴파일하면 `CASE WHEN (chunks.content %> %(param_1)s::VARCHAR) THEN word_similarity(%(param_2)s::VARCHAR, chunks.content) ELSE … END` 꼴이고, 두 자리에 서로 다른 파라미터가 들어가서 DB가 한 번으로 합치지 못한다. WHERE의 재확인(Recheck)까지 더하면, 맞는 행 하나에서 낱말 1개당 trigram 계산이 최대 3번 일어난다.
  — 위치: backend/app/search/keyword.py:28-31 `_term_score`, :37-72 `KeywordSearcher.search` · backend/app/db/session.py:26-33 `create_db_engine` · backend/app/api/search.py:44-55 `search` · backend/app/config.py:38
  — 확인한 범위: 패킷 실측과 EXPLAIN, keyword.py와 같은 식을 psycopg 방언으로 컴파일한 SQL(scratchpad 스크립트로 DB 없이 컴파일만 함, 실행 안 함), session.py 전체, config.py 상한값. 실제 사용자 기록 크기는 모른다. 조각 1만 개는 최악에 가까운 가정이라 실제 사용에서는 훨씬 짧을 수 있다. 그래서 등급을 [위험]이 아닌 [주의]로 했다.
  — 고치는 방법:
    ① 검색 쿼리 앞에 `SET LOCAL statement_timeout = '…'`을 건다(PostgreSQL일 때만, KeywordSearcher.search 안). 시간 초과(OperationalError / QueryCanceled)가 나면 rollback 뒤 "검색이 오래 걸려 멈췄어요" 같은 응답(예: 503)으로 바꾸고, 로그 저장은 rollback 다음에 한다. 초 수를 사용자가 정해야 하면 Q로 올린다.
    ② 낱말별 비슷함을 한 번만 계산한다. 예를 들어 서브쿼리에서 `word_similarity(낱말_i, content) AS s_i`를 한 번 구하고, 서브쿼리가 펼쳐져 식이 다시 복사되지 않게 `OFFSET 0`을 붙인다. 바깥에서는 `CASE WHEN s_i >= current_setting('pg_trgm.word_similarity_threshold')::float THEN s_i ELSE 0 END`를 더한다(`%>`와 같은 기준). WHERE의 `%>`는 색인을 타야 하므로 그대로 둔다. 고친 뒤 같은 데이터로 다시 재서 비교한다.
    ③ (선택) 사용자별 검색 횟수 상한을 둔다. 설계 원칙 4는 LLM 호출 기준이라, 검색에도 상한을 둘지는 사용자가 정할 일이다 → OPEN_QUESTIONS 후보.
  — 참고(실측 해석, [추정]): 패킷의 "맞는 것 없음: SQL 0.6ms인데 search()는 1.1초"는 실행 계획 차이보다 호출마다 붙는 고정 비용일 가능성이 크다. `useEffect`에서도 search()(3,268ms)와 SQL 단독(2,189ms)의 차이가 약 1.08초로 같기 때문이다. 실행 계획이 달라 색인을 안 탔다면, 맞는 행이 많은 `useEffect`에서는 차이가 거의 없어야 한다. 측정 스크립트의 연결 열기나 첫 호출 비용을 의심한다. 같은 세션으로 search()를 연달아 두 번 불러 두 번째 시간을 재면 구분된다. 그래도 남으면 search()가 내보내는 SQL을 그대로(JOIN과 `::VARCHAR` 포함, psycopg의 자동 prepare가 5번째 호출부터 켜지는 것 포함) EXPLAIN ANALYZE 한다.

- [제안] [추정] 노트 ID 범위를 검사하지 않아서, 아주 큰 숫자를 넣으면 404 대신 500(또는 422)이 된다. ([확실]로 만들려면: PostgreSQL에서 `GET /api/notes/2147483648`을 한 번 불러 500인지 본다.)
  백엔드의 `note_id: int`(notes.py:125)에는 범위가 없다. SQLAlchemy psycopg 방언은 비교값을 `%(…)s::INTEGER`로 형변환해 보낸다(위 컴파일에서 `notes.user_id = %(user_id_1)s::INTEGER` 확인, notes.id도 Integer). 그래서 2147483648 이상이면 PostgreSQL이 "integer out of range"로 실패하고, 처리되지 않은 DataError가 500과 서버 오류 로그를 남긴다고 본다. 화면(records/[noteId]/page.tsx)은 `DIGITS_ONLY`(:13)에 자릿수 제한이 없다. 그래서 아주 긴 숫자는 `Number()`(:28)가 `1e+21` 꼴로 바꾸고, 백엔드가 422를 돌려준다. 어느 쪽이든 화면에는 "노트를 불러오지 못했어요"가 나온다(없는 노트인데 오류처럼 보임). 남의 데이터가 보이거나 응답에 내부 정보가 나가지는 않는다(FastAPI 기본 500 문구, engine hide_parameters=True).
  — 위치: backend/app/api/notes.py:124-130 `get_note` · frontend/src/app/(app)/records/[noteId]/page.tsx:13, 24, 28, 46
  — 확인한 범위: notes.py 경로 매개변수 선언, psycopg 방언의 바인드 형변환(컴파일로 확인), page.tsx의 정규식과 Number 변환. PostgreSQL 실행은 하지 않았다(개발 · 테스트 DB 사용 금지).
  — 고치는 방법: 백엔드는 `note_id: int = Path(ge=1, le=2_147_483_647)`로 범위를 막거나, 범위 밖이면 바로 404를 돌려준다("없는 노트"와 같은 응답이 의도에 더 맞음). 화면은 `/^\d{1,10}$/`처럼 자릿수를 막고 범위 밖이면 `notFound()`를 부른다. `chunk` 매개변수(:46)도 같은 정규식을 쓴다.
