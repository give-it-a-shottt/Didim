## 지적

(3차 대비: R(이미지) · S(링크 정규식)는 해결됨. P(마크다운 렌더링 비용 · 스택 넘침)는 **일부만 해결** — 평범한 노트와 "본문 속" 병적 입력의 비용은 크게 줄었지만, 아래 1 · 2 · 3의 길이 남았다. 2는 3차 P의 남은 부분이라 [신규]를 붙이지 않았고, 1 · 3은 이번에 새로 생긴 코드 경로(조각 사이 빈 구간 · 울타리 합치기)에서 나온 것이라 [신규]다.)

측정 방법(1~3 공통): note-markdown.tsx(4차)의 `toUtf16Offsets` · `splitByChunks` · `mergeOpenFences` · `COMPONENTS`(block 래퍼 포함) 로직을 그대로 옮긴 scratchpad 사본(r2js4/render.mjs)을 만들고, 조각 위치는 레포 venv로 **실제 `split_markdown`**(backend/app/services/chunking.py, max_chunks=2000)을 돌려 얻었다(r2js4/gen.py · gen2.py). 레포 node_modules(react-markdown 10.1.0 · remark-gfm 4.0.1)로 Node 22.17 `renderToString`, 이 PC에서 잼. Next의 RSC 렌더링 경로와는 다르므로 실제 서버 수치는 다를 수 있다.

1. [신규] [주의] [확실] 제목만 있는 줄은 조각이 되지 않아(chunking.py 규칙 4) "조각 사이 빈 구간"으로 남고, 그 구간은 길이 제한 없이 `<Markdown>` 한 번에 통째로 그려진다. 그래서 조각 단위 격리를 우회해 3차와 같은 서버 멈춤이 그대로 난다.
   - 위치: frontend/src/components/note-markdown.tsx:67 · 71(빈 구간을 그대로 묶음으로 넣음), :164-175(200,000자 이하면 묶음 길이와 상관없이 Markdown), backend/app/services/chunking.py:165-166(`has_body` 없는 구역 건너뜀), backend/app/importers/markdown.py:23 · 79-89(제목 줄 길이 제한 없음), backend/app/services/import_service.py:118(조각 1개만 있으면 저장됨)
   - 확인한 범위: 원문 = `# ` + 병적 글자 한 줄 + `\n## b\n본문\n`(199,0xx자, 조각 1개 · 덮인 글자 7자 · 빈 구간 198,983자). 결과: `# *a…` 20,000자 1.2초 · 50,000자 8.2초 · 199,000자 60초 넘어 중단, `# _a*…` 199,000자 60초 넘어 중단, `# [a](…` 199,000자 7.4초. 3차의 `*a` 50KB 7.2초와 같은 제곱 증가라, 200,000자 상한은 1MB→200KB로 줄였을 뿐 이 입력 모양에는 효과가 없다. 같은 이유로 조각 위치가 원문과 안 맞아 `splitByChunks`가 모든 조각을 건너뛰면(:58-60, 정상 데이터에서는 없음) 원문 전체가 한 묶음이 된다.
   - 고치는 방법: 묶음 하나의 길이에도 상한을 둔다 — 조각이 아닌 묶음(`chunkIds`가 빈 것)이나 `MAX_MERGED_SEGMENT_CHARS`(또는 조각 기준 1,500자 + 여유)를 넘는 묶음은 마크다운 대신 글자 그대로(`whitespace-pre-wrap`) 그린다. 빈 구간은 제목 · 공백뿐이라 글자 그대로 보여도 잃는 것이 적다. `# ` + `*a` 5만 자 같은 입력으로 테스트를 하나 둔다.

2. [주의] [확실] 묶음마다 비용은 갇혔지만 요청 하나의 **총 비용**에는 상한이 없다. `>` 반복 원문은 조각 133개 × 약 110ms로 서버를 7초 넘게 멈추고 HTML이 7MB를 넘는다.
   - 위치: frontend/src/components/note-markdown.tsx:169-178(모든 묶음을 차례로 렌더링, 시간 · 깊이 상한 없음), :15(`MAX_MARKDOWN_RENDER_CHARS = 200_000`)
   - 확인한 범위: 실제 조각 나누기로 잰 199,000자 원문(조각 수 · 렌더링 총 시간 · 가장 느린 묶음 · HTML 길이): 평범한 노트(제목 · 문단 · 목록 · 표 반복) 1,668조각 1.2초 · 10ms · 0.74MB, `*a` 반복 133조각 1.3초 · 44ms, `_a*` 반복 133조각 1.8초 · 30ms, `>` 반복 133조각 **7.2초** · 112ms · **7.4MB**(1,500단 중첩 인용 133개). 3차(1MB 평범한 노트 11초, `*a` 1MB 60초+)보다 크게 나아졌지만, 로그인한 사용자 누구나 200KB 이하 `.md` 하나로 여는 때마다 Next 서버 전체를 수 초 멈출 수 있는 길이 남았다.
   - 고치는 방법(대안): ① 렌더링 시간 예산 — 묶음을 그리기 전 누적 시간(`performance.now()`)이 예: 300ms를 넘으면 남은 묶음은 글자 그대로 그린다(입력 모양과 상관없이 총량이 묶임. 1과 같이 쓰면 묶음 하나의 최악도 막힘). ② 모양 검사 — 줄 앞의 `>` · 목록 들여쓰기 깊이가 예: 20단을 넘는 묶음은 글자 그대로. ③ 3차 대안 ②(클라이언트 렌더링)로 비용을 그 사람 브라우저로 옮김. 어느 것을 쓸지는 사용자 선택(D-017에 추가 기록 후보).

3. [신규] [제안] [확실] 울타리 합치기의 상한 8,000자는 스택 넘침을 막지 못한다. 실제 컴포넌트(block 래퍼)를 쓰면 `>` 2,000단부터 `RangeError: Maximum call stack size exceeded`가 나고, 울타리 개수 세기가 CommonMark와 달라 `>`를 8,000자 가까이 한 묶음에 모을 수 있다.
   - 위치: frontend/src/components/note-markdown.tsx:16-17(주석 "약 1만 자부터"), :75-79(`FENCE_LINE`으로 줄 머리 ``` · ~~~ 개수만 셈), :86(합치기 조건)
   - 확인한 범위: 원문 `` ```a``` `` + 줄바꿈 + `>`×N. `` ```a``` ``는 CommonMark에서 울타리가 아니지만(백틱 울타리의 정보 문자열에 백틱 불가) `FENCE_LINE`은 1개로 세어 "열린 울타리"로 보고 다음 조각들을 8,000자까지 합친다.    - 고치는 방법: 합친 묶음 상한을 조각 기준(1,500자) 근처로 낮추거나, 2의 ② 모양 검사(인용 · 목록 깊이)를 합친 묶음에도 적용한다. 주석의 "약 1만 자" 근거를 실제 컴포넌트 기준 값으로 고친다. `` ```a``` `` + `>` 반복 입력으로 테스트를 하나 둔다.
