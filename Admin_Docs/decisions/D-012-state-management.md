# D-012 상태 관리 기준 — 서버 상태는 TanStack Query, 여러 화면이 같이 쓰는 UI 상태만 Zustand

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 사용자가 골랐어요(2026-11-09).
무엇을: 화면이 다루는 값을 세 종류로 나눠서 각자 정해진 곳에 둬요. 서버에서 온 데이터(노트 · 카드 · 공고 · 자소서)는 TanStack Query가 맡아서 캐시해요. 여러 화면이 같이 봐야 하는 화면 상태만 Zustand(전역 상태)에 둬요. 화면 하나에서만 쓰는 값은 그 화면 안에 둬요. 비유하면 도서관 책(서버 데이터)은 대출 기록으로 관리하고, 가족이 같이 보는 냉장고 메모(전역 상태)만 거실에 붙이고, 내 책상 메모(지역 상태)는 내 방에 둬요.
왜 (사용자 확인): 서버 상태(TanStack Query)와 전역 상태(Zustand)를 구분해서 꼭 필요할 때만 쓰고, 각각 왜 그렇게 관리했는지 기록해 두어 그 판단이 맞는지 확인받을 수 있게 한다.

## 개발자 상세

### 상황
- App Router(Next.js 16)를 유지한다(사용자 선택, 2026-11-09 — 추천을 받아들임). 서버 컴포넌트가 데이터를 직접 가져올 수 있어서, 모든 데이터를 클라이언트 라이브러리로 가져올 필요는 없다.
- 사용자는 TanStack Query와 Zustand를 쓰되, 쓰는 이유를 설명할 수 있기를 원했다.

### 기준
| 값의 종류 | 어디에 | 예시(예상) |
|---|---|---|
| 처음 화면을 그릴 때 필요한 서버 데이터 | 서버 컴포넌트에서 가져옴 | 노트 상세 첫 화면 |
| 화면에서 자주 바뀌거나 다시 불러야 하는 서버 데이터, 수정(mutation) | TanStack Query | 퀴즈 답 제출, 자소서 편집 · 근거 검사, 가져오기 진행 상태 확인 |
| 여러 화면이 같이 쓰는 UI 상태 | Zustand | 기록 추가 모달 열림 · 처리 진행(어느 화면에서든 열리고 화면을 옮겨도 이어 보임), 자소서 화면 사이드바 접힘 |
| 화면 하나에서만 쓰는 값 | 컴포넌트 안(useState) | 입력 중인 글자, 탭 안의 열림 · 닫힘 |

- 서버 데이터를 Zustand에 복사하지 않는다(두 곳에 있으면 어긋난다).
- Zustand는 선택 구독(selector)으로 필요한 조각만 읽는다.
- 쓸 때마다 [architecture.md](../overview/architecture.md)의 "상태 관리 지도"에 무엇을 · 어디에 · 왜를 한 줄 남긴다.
- 두 패키지는 처음 필요한 기능에서 설치한다(패키지 추가라 R2 리뷰).

### 최적화라고 말할 수 있는 범위
- TanStack Query 캐시 → 같은 데이터 중복 요청 감소 = 네트워크 최적화
- Zustand 선택 구독 → 바뀐 조각을 쓰는 컴포넌트만 다시 그림 = 렌더링 최적화
- props를 아래로 안 내리는 것(prop drilling 제거) 자체는 구조 · 유지보수 개선이지 성능 최적화가 아니다.

### 후보
| | A. 서버 컴포넌트 + TanStack Query + Zustand(구분해서) | B. 모든 데이터를 Zustand에 | C. Context만 |
|---|---|---|---|
| 장점 | 데이터 종류마다 맞는 도구, 이유를 설명하기 쉬움 | 도구 하나 | 패키지 없음 |
| 단점 | 도구가 세 가지라 기준을 지켜야 함 | 캐시 · 다시 불러오기 · 로딩 상태를 직접 짜야 함, 서버 데이터와 어긋남 | 값이 바뀌면 구독한 컴포넌트가 다 다시 그려짐 |

### 결정
- A.

### 이 결정을 바꿔야 하는 조건
- 전역 UI 상태가 1~2개에서 늘지 않으면 Zustand 대신 Context로 줄이는 것을 검토한다.
