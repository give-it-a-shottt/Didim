# T-008 PostgreSQL 17에서 검색 쿼리 최적화가 의도대로 안 됨 (OFFSET 0 · 색인 선택)

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 해결했어요(2026-11-10).
무슨 문제였나: 기록 검색을 빠르게 하려고 리뷰가 제안한 방법(서브쿼리 + `OFFSET 0`)을 썼는데, PostgreSQL 17에서는 효과가 없었어요. 또 실제 앱처럼 값을 묶어 보내면, 맞는 결과가 없어도 내 조각을 전부 계산하는 느린 방법을 DB가 골랐어요.
어떻게 해결했나: 후보를 한 번만 고르게 쿼리 구조를 바꾸고(MATERIALIZED), 색인을 "사용자 + 본문" 하나로 합쳤어요. 색인 파일(0003)을 고쳐서 개발 DB에 다시 올렸어요.

## 개발자 상세

### 1. 서브쿼리 + `OFFSET 0`이 울타리가 안 됨
- 증상: 후보 고르기를 서브쿼리에 넣고 `OFFSET 0`으로 펼침을 막으려 했지만, EXPLAIN에서 서브쿼리가 바깥 쿼리로 펼쳐져 있었음.
- 해결: `WITH … AS MATERIALIZED` CTE로 후보를 한 번만 고르고, 낱말별 비슷함도 한 번만 계산 → 상위 limit개에만 본문 · 제목을 붙임(F-003 1차 리뷰 A).
- 재발 방지: "쿼리 울타리" 같은 플래너 요령은 버전마다 다르니 EXPLAIN으로 확인한 뒤 쓴다. 명시적인 `MATERIALIZED`를 먼저 쓴다.

### 2. 값을 묶어 보내면 플래너가 user_id 색인 + 행마다 거르기를 고름
- 증상: 리터럴 값으로 EXPLAIN하면 괜찮은데, 실제 앱처럼 값을 묶어(바인드 파라미터) 실행하면 user_id 색인으로 내 조각을 다 읽고 행마다 비슷함을 계산함 → 맞는 게 없어도 느림.
- 해결: 색인을 `GIN (user_id, content gin_trgm_ops)` 하나로 합침(`btree_gin` 확장 추가). 버전 파일 0003을 고침.
- 개발 DB 반영: 이미 0003이 올라간 개발 DB는 `alembic downgrade 0002` 뒤 `alembic upgrade head`로 다시 올림(검색 로그 0건이라 지워질 데이터 없음, F-003 feature.md 기록).
- 재발 방지: 검색 속도는 실제 앱과 같은 방식(값을 묶어 보내기)으로 잰다. 이미 적용된 버전 파일을 고치는 건 개발 단계 · 데이터가 없을 때만 하고, 그 뒤로는 새 버전 파일을 만든다(D-015).
- 남은 확인: 배포 DB에서 `pg_trgm` · `btree_gin` 확장 설치 권한(Q-012).
