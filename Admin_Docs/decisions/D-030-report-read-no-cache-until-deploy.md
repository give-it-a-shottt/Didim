# D-030 평가 리포트 읽기는 배포를 정할 때까지 캐시하지 않는다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 사용자가 추천안을 골랐어요(2026-11-19, F-011 · F-010 '다음에 고칠 것').
무엇을: 랜딩 첫 화면 수치와 `/report`는 지금처럼 열 때마다 백엔드 `GET /api/report`를 새로 읽어요(`no-store`). 캐시를 붙일지는 배포(Q-012)를 정할 때 다시 봐요.
왜 (사용자 선택): Next 16에서 `"use cache"`를 붙이면 결과가 빌드 때 정적 셸에 들어가서, 빌드할 때 백엔드가 꺼져 있으면 '못 읽음'이 화면에 굳을 수 있어요. 배포 방식이 아직 안 정해져서 이 위험을 지금 판단할 수 없어요. 백엔드는 DB 없이 요약 json 몇 개만 읽어서 요청마다 읽어도 부담이 작아요.

## 개발자 상세

### 배경
F-011 3차 리뷰 R2 제안: 공개 랜딩을 열 때마다(검색 로봇 포함) `/api/report`를 `no-store`로 부른다. 수치는 평가 회차를 새로 돌릴 때만 바뀐다. 캐시 범위는 사용자에게 먼저 묻기로 했다.

### 후보
| 후보 | 장점 | 단점 |
|---|---|---|
| A. 지금은 캐시 안 함 (선택) | 코드 그대로, 백엔드가 고장 나도 다음 요청에서 바로 회복, 실패 테스트가 단순 | 방문마다 백엔드 요청 1번(요약 파일 읽기) |
| B. `getReportRuns`에 `"use cache"` + `cacheLife('hours')` | 랜딩 수치가 정적 셸에 들어가 빠름, 백엔드 요청이 몇 시간에 한 번 | 빌드 때 백엔드가 필요, 실패를 캐시하지 않으려면 던지고 바깥에서 잡는 처리가 더 필요, 고장 테스트가 빌드에 묶여 어려움, 백엔드만 다시 배포하면 몇 시간 옛 수치 |
| C. 백엔드에서 요약 폴더 수정 시각 기준 캐시 | 화면 쪽 그대로 | 파일 읽기 자체가 가벼워 얻는 것이 작음 |

### 결정
- `lib/report-data.ts`의 `getReportRuns`는 `fetchBackendPublic`(`cache: "no-store"`) 그대로 둔다.
- 리포트를 통째로 못 읽을 때의 화면은 e2e로 지킨다: `tests/report-unavailable.spec.ts` — 같은 빌드를 두 번째 `next start`(3101)로 띄우고, 그 서버만 모든 요청에 500을 주는 가짜 백엔드(8101)를 보게 한다. 화면 서버가 백엔드를 직접 불러 `page.route`로는 못 가로채고, 가짜 백엔드 하나에 '고장' 스위치를 두면 병렬로 도는 다른 테스트까지 고장 나기 때문이다.

- 덧붙임(사용자 선택 2026-11-19, F-011 6차 리뷰 R4): 화면은 응답의 회차 · 평가 · 수치 모양까지 검사하고(`lib/report.ts` isReportRuns), 회차 하나라도 틀리면 응답 전체를 '못 읽음'으로 본다. 틀린 회차만 건너뛰면 최신 회차가 틀렸을 때 옛 회차가 '최근 회차'처럼 보여서다. 백엔드(`report.py`)는 회차마다 검사해 틀린 회차를 빼므로 두 방식은 백엔드 · 화면 버전이 어긋날 때만 갈린다. 다른 방법 — 화면도 틀린 회차만 건너뛰기 — 은 고르지 않았다.

### 이 결정을 바꿔야 하는 조건
- 배포(Q-012)를 정할 때: 빌드 환경에서 백엔드에 닿는지, 백엔드만 따로 다시 배포하는지 보고 B를 다시 본다.
- 공개 랜딩 요청이 많아져 백엔드 부담이 보이면 B나 C를 다시 본다.
