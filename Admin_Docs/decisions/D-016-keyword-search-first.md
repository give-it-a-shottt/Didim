# D-016 기록 검색은 키워드 검색으로 시작하고, 임베딩은 평가로 비교한 뒤 붙인다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 사용자가 골랐어요(2026-11-10).
무엇을: F-003(기록 검색 + 근거)은 처음에 "같은 낱말이 들어 있는 조각 찾기"(키워드 검색)로 만들어요. 뜻으로 찾는 임베딩 검색은 끼워 넣을 자리만 만들어 두고, 평가 세트로 "키워드만으로 충분한지"를 수치로 본 뒤에 붙일지 정해요.
왜: 무료이고 빠르며, 공부 기록을 바깥 서비스로 보내지 않아요. EXAONE API에는 임베딩이 없고, 구글 무료 임베딩은 호출 제한 때문에 여러 개를 올리면 느려졌어요. 그리고 "벡터 검색이 정말 필요한가"를 수치로 보여 주는 것 자체가 이 프로젝트의 목표(평가로 증명)에 맞아요. (사용자가 고른 안)

## 개발자 상세

### 상황
- D-008: 저장 · 검색은 PostgreSQL + pgvector 하나로, "키워드(BM25)와 벡터를 섞을지는 2주차에 비교해서 정한다".
- D-014: LLM은 K-EXAONE 2.5. EXAONE API에는 임베딩이 없다 → Q-002로 따로 정해야 했다.
- 사용자 경험: 구글(Gemini) 무료 임베딩은 조금만 써도 느려졌다(호출 제한).

### 후보
| | A. 키워드로 시작 + 나중 비교 | B. 로컬 오픈소스 임베딩 | C. 구글 Gemini 무료 임베딩 |
|---|---|---|---|
| 방식 | PostgreSQL 키워드 검색. 임베딩은 교체 구조로 자리만 | multilingual-e5-small · bge-m3 등을 서버에서 직접 실행 | 구글 API로 조각마다 임베딩 |
| 장점 | 무료 · 빠름 · 기록이 밖으로 안 나감 · 새 서비스 없음 | 무료 · 호출 제한 없음 · 기록이 밖으로 안 나감 · 뜻으로 찾음 | 품질 좋음 · 서버 부담 없음 |
| 단점 | 뜻은 같고 낱말이 다르면 못 찾음 | 서버 메모리 · CPU 필요, 배포 위치(Q-012)에 영향 | 분당 호출 제한(느려짐), 무료 등급은 보낸 내용이 서비스 개선에 쓰일 수 있음(약관 확인 필요 [추정]) |

### 결정
- A. F-003은 키워드 검색으로 시작한다.
- 구체 방식은 F-003 설계 때 정한다. 참고: PostgreSQL 기본 전문 검색은 한국어 형태소를 모르고 띄어쓰기로만 나눠서 "useEffect를" 같은 조사 붙은 낱말을 놓치기 쉽다. 부분 일치(pg_trgm)가 후보.
- 검색은 LLM(D-014)처럼 갈아 끼울 수 있는 구조로 만든다(키워드 → 나중에 벡터 · 섞기). 모든 검색에 user_id 조건(D-004).
- 검색 결과는 평가 세트로 채점할 수 있게 로그를 남긴다(D-005, 설계 원칙 5). 이 점수가 임베딩을 붙일지의 근거가 된다.

### 결과로 생기는 제약
- 2주차에 `chunks.embedding`(pgvector) 컬럼은 만들지 않는다. 임베딩을 붙이기로 하면 그때 Alembic 버전 파일로 추가한다(D-015).
- 평가 세트에 "뜻은 같고 낱말이 다른" 질문을 넣어야 키워드 검색의 약점이 수치로 드러난다.

### 이 결정을 바꿔야 하는 조건
- 평가 세트에서 키워드 검색이 놓치는 근거가 많을 때(기준 점수는 F-003 · F-010 평가 설계 때 정함) → B 또는 C를 붙여 비교한다. C를 고르면 무료 등급 약관(보낸 내용 사용 여부)부터 확인한다.
