# D-010 구글 로그인은 FastAPI가 처리한다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 사용자가 골랐어요(2026-11-07).
무엇을: 구글 로그인으로 신분을 확인하고 출입증(httpOnly 쿠키)을 주는 일과, 매 요청마다 출입증을 확인하는 일을 둘 다 FastAPI 서버가 해요. Next.js 화면은 브라우저가 들고 있는 쿠키를 그대로 실어 보내기만 해요. 비유하면 금고가 있는 사무실(FastAPI)이 출입증 발급과 확인을 함께 맡고, 로비 안내데스크(Next.js)는 안내만 해요.
왜 (사용자 확인): 처음에는 인증(사용자 검사)과 데이터를 지키는 곳을 따로 두려고 했다. 하지만 혼자 관리하는 프로젝트라서, 관리 측면에서 둘을 FastAPI 서버 한 곳에 묶는 게 좋겠다고 생각했다.

## 개발자 상세

### 상황
- [D-004](D-004-multi-user-from-day-one.md)로 1주차부터 로그인과 사용자별 데이터 분리를 넣는다. 로그인은 구글 로그인으로 시작한다([F-001](../features/F-001-account-isolation/feature.md)).
- 모든 조회 · 벡터 검색의 user_id 조건은 FastAPI에서 건다. 그래서 "누가 요청했는지"를 어디서 정할지가 문제였다.

### 후보
| | A. Next.js(Auth.js)가 로그인 처리 | B. FastAPI가 로그인 처리 |
|---|---|---|
| 흐름 | Next.js가 구글 로그인 후 토큰 발급, FastAPI는 토큰을 검증해 user_id를 꺼냄 | FastAPI가 구글 OAuth를 끝까지 처리하고 httpOnly 세션 쿠키 발급 · 검증 |
| 장점 | 라이브러리가 흐름을 대신 처리해 빠름 | 사용자 확인과 데이터 분리가 한 서버에 있음, 비밀키가 한 곳에만 있음 |
| 단점 | 인증이 두 서버에 나뉨. 같은 비밀키를 나눠 쓰면 둘 중 하나만 뚫려도 출입증 위조 가능 | OAuth 흐름(리다이렉트, state 검사)을 직접 구현해야 함 |

### 결정
- B. FastAPI가 구글 로그인 · 세션 발급 · 매 요청 확인을 맡는다. 세션은 httpOnly 쿠키로 주고, 브라우저 저장소(localStorage)에 토큰을 두지 않는다.

### 보안 관점 메모
- 나누는 게 안전해지려면 "두 곳을 모두 뚫어야 열리는" 구조여야 한다. A(같은 비밀키 공유)는 Next.js만 뚫려도 출입증 위조, FastAPI만 뚫려도 DB 접근이 되어 털리는 길이 2개다. B는 1개다.
- FastAPI가 뚫리면 데이터가 털리는 건 A · B 같다. 그래서 FastAPI 쪽 방어(비밀값은 환경변수만, 모든 조회에 user_id 조건, 사용자 간 분리 테스트)를 R2 리뷰에서 매번 확인한다.

### 결과로 생기는 제약
- 로그인이 필요한 모든 API는 FastAPI에서 세션 쿠키를 확인한 뒤 user_id를 정한다. 요청 본문이나 주소에 담긴 user_id는 믿지 않는다.
- 화면(Next.js)과 서버(FastAPI)의 주소가 다르면 쿠키 전달 설정(CORS 허용 출처, 쿠키 SameSite)을 맞춰야 한다. 1주차 구현 때 정한다.

### 이 결정을 바꿔야 하는 조건
- 서비스가 여러 개로 늘어 로그인 하나로 같이 써야 할 때 → 로그인 전용 서버를 따로 둔다.
- 로그인을 전문 인증 서비스(Auth0, Cognito, Supabase Auth 등)에 맡기기로 할 때 → 공개키 방식으로 FastAPI는 확인만 한다.
- 팀이 생기거나 로그인 요청만 따로 늘려야 할 만큼 사용자가 많아질 때.
