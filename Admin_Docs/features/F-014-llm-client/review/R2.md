## 지적
- [주의] [확실] `complete_json` 한 번의 최악 대기 시간에 상한이 없다. 타임아웃 60초는 httpx의 read 타임아웃이라 "바이트 사이 간격" 기준이고 전체 시간이 아니며, 형식 재시도 2번 × 연결 재시도 2번 = HTTP 최대 4번이라 응답이 안 오는 정상 경우만 쳐도 약 4 × (연결 5초 + 읽기 60초) + 대기 2초 ≈ 4분 20초, 서버가 조금씩 흘려 보내면 그 이상도 기다린다. 첫 사용 기능이 요청 안에서 바로 부르면 사용자가 몇 분씩 기다리게 된다. — 위치: backend/app/llm/openai_compat.py:96-115, backend/app/llm/structured.py:110-124, backend/app/llm/settings.py:30-36 — 확인한 범위: 패킷의 세 파일 코드와 httpx Timeout 의미(read는 청크 사이 간격). 실제 서버로는 재현하지 않음 — 고치는 방법: `complete_json`(또는 chat) 전체를 `asyncio.timeout(LLM_TOTAL_DEADLINE_SECONDS)`로 감싸 넘으면 LLMUnavailable로 바꾸고, 남은 시간이 없으면 재시도하지 않게 한다.
- [주의] [확실] 코드 블록 정규식 `_FENCE_RE`가 공백 · 탭이 길게 이어진 답에서 제곱 시간이 걸리고, async 함수 안에서 동기로 돌아 그동안 서버 전체(이벤트 루프)가 멈춘다. "```"로 시작한 뒤 공백이 이어지는 답(모델이 공백을 반복하다 길이 제한에 걸리는 흔한 고장)에서 공백 4,000자 0.08초 → 8,000자 0.32초 → 16,000자 1.26초로 길이의 제곱으로 늘었다. — 위치: backend/app/llm/structured.py:26, 40 — 확인한 범위: 같은 정규식만 따로 떼어 로컬 Python으로 시간 측정(레포 코드 · 테스트는 실행하지 않음) — 고치는 방법: 정규식 대신 문자열 처리로 바꾼다(앞이 ``` 이면 첫 줄 제거, 뒤가 ``` 이면 끝 3글자 제거 후 strip). 함께 답 길이 상한(예: 일정 글자 수 넘으면 바로 형식 오류)을 두면 더 안전하다.
- [주의] [확실] 비용 상한(원칙 4)용 집계가 실제보다 적다. `StructuredReply.attempts`는 형식 재시도 횟수만 세서 연결 재시도로 실제 HTTP 호출이 4번이어도 2로 나오고(주석은 "실제로 AI를 부른 횟수"), 토큰도 마지막 성공 답(`reply`)의 것만 남아 앞서 틀린 답의 토큰이 빠진다. 실패(LLMInvalidOutput · LLMRateLimited · LLMUnavailable)로 끝나면 그때까지 쓴 호출 · 토큰이 전혀 돌려지지 않는다. 시간 초과 재시도는 서버가 이미 답을 만들어 과금했을 수 있어서 빠지면 더 크게 어긋난다. — 위치: backend/app/llm/structured.py:30-34, 110-130, backend/app/llm/openai_compat.py:101-115 — 확인한 범위: 패킷의 두 파일과 test_llm.py의 attempts 확인 테스트 — 고치는 방법: 호출마다 사용량(HTTP 요청 수 · prompt/completion 토큰 합)을 누적하는 작은 객체를 두고 StructuredReply와 LLMError 하위 예외 모두에 붙여, 부른 기능이 성공 · 실패 상관없이 상한에 더할 수 있게 한다.
- [제안] [확실] 응답 본문이 깊게 중첩된 JSON이면 `response.json()`이 ValueError가 아닌 RecursionError를 내는데, `_parse_reply`가 ValueError만 잡아서 LLMError 분류 · 재시도를 건너뛰고 날것의 예외로 올라간다(부르는 쪽이 `except LLMError`로 못 잡음). 믿을 수 있는 EXAONE에서는 드물지만 local 서버 · 프록시 오류 페이지 같은 비정상 응답을 막는 목적에 어긋난다. — 위치: backend/app/llm/openai_compat.py:154-157 — 확인한 범위: 로컬 Python에서 `json.loads`에 깊은 중첩 배열을 넣어 RecursionError(ValueError 아님) 확인, httpx `Response.json()`이 json.loads를 쓰는 것은 기억 기준 — 고치는 방법: `except (ValueError, RecursionError)`로 같이 잡아 `_TransientError("invalid response body")`로 바꾼다.
- [제안] [확실] "오류 문구에 받은 내용을 넣지 않는다"(base.py:13, structured.py:51)는 약속이 일부 깨질 수 있다. `include_input=False`여도 pydantic 오류의 loc에는 AI 답이 만든 키 이름(허용 안 된 추가 키, `dict[str, ...]` 칸의 키)이, msg에는 구분자 값(`Input tag '...' found using ...`)이 그대로 들어가서 LLMInvalidOutput 문구 → 로그로 갈 수 있다. 지금 스키마는 없어서 실제 영향은 첫 기능의 스키마 모양에 달려 있다. — 위치: backend/app/llm/structured.py:50-59, 126-128 — 확인한 범위: backend/.venv의 pydantic으로 extra="forbid" · dict 키 · 구분자 유니온 세 경우를 직접 검사해 값이 loc · msg에 나오는 것을 확인 — 고치는 방법: 예외 문구에는 loc의 정수 · 스키마 필드 이름과 `error["type"]`(예: missing, int_parsing)만 쓰고, msg 전체는 재요청 메시지(어차피 AI가 만든 내용이 AI로 돌아가는 곳)에만 쓴다.
