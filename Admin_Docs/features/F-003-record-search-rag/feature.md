# F-003 기록 검색과 근거 표시 (RAG)

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 2차 리뷰 [통과], 평가 기준선 기록 — 낱말이 겹치면 1.00, 낱말이 다르면 0.60(2026-11-10).
언제: 2주차
무엇을: 질문하면 기록 조각(F-002)에서 관련 조각을 찾아 원문 위치와 함께 보여 줘요. 처음은 키워드 검색, 임베딩은 평가로 비교한 뒤(D-016)
왜: 관련 기록을 원문 위치까지 찾아 주고, 공고 매칭 · 자소서 · 면접이 근거를 찾을 때도 이 검색을 쓰려고요.

## 설계 의도 (사용자 확인 — 코드 작성 전에 채움, 문장 정리사 사용)
- 이 기능이 해결하는 문제: 낱말이나 문장을 넣으면 내 기록에서 관련 조각을 찾아, 그 조각이 원문 어디에 있는지까지 보여 준다. 공고 매칭 · 자소서 · 면접이 근거를 찾을 때도 같은 검색을 쓴다. (사용자 확인, 2026-11-10)
- 완료 기준(2주차): (사용자 확인, 2026-11-10)
  1. 낱말 · 문장을 넣으면 내 기록 조각 최대 5개. 결과마다 노트 제목 · 제목 경로 · 원문 위치.
  2. 다른 사용자의 조각은 나오지 않는다(테스트, D-004).
  3. 결과를 누르면 노트 상세에서 그 조각 위치로 가서 강조한다.
  4. 검색마다 질문 · 결과 조각 · 점수를 로그로 남긴다(D-005).
  5. 내 기록으로 만든 질문 20개 평가 세트에서 '상위 5개 안에 정답 조각이 있는 비율'을 재서 기록한다. 목표 숫자는 없고, D-016 임베딩 비교의 출발점이다. 질문 · 정답은 사용자가 정한다(일부는 '뜻은 같고 낱말은 다른' 질문).
  6. 검색 방식은 갈아 끼울 수 있다(키워드 → 나중에 임베딩, D-016).
- 검색 대상: 2주차는 기록 조각만. 경험 카드는 F-006 때 추가. (사용자 확인)
- 화면 · 컴포넌트: (사용자 확인, 2026-11-10)
  - 작은 검색창: 기록 · 복습 홈(REV_01_001) 노트 목록 위. 새 화면 · 새 주소 없음(didim-design.md IA에 반영).
  - 결과 줄: 노트 제목 · 제목 경로 · 조각 발췌(명조 — 내 기록 원문, 찾은 낱말 표시).
  - 노트 상세(REV_01_002): 원문을 보여 주고 고른 조각 위치를 강조. 이 '근거 → 원문 위치'는 이후 퀴즈 · 자소서 · 면접의 근거 칩에서 다시 쓴다.
- API: `GET /api/search?q=…&limit=5` → 조각 목록(조각 · 노트 ID, 노트 제목, 제목 경로, 시작 · 끝 위치, 발췌, 점수). 검색어를 주소(`?q=`)에 담아 서버 컴포넌트로 결과를 그린다(검색어가 접속 기록에 남을 수 있음을 알고 고름). 노트 상세용 `GET /api/notes/{id}`(원문 포함, user_id 조건). (사용자 확인, 2026-11-10)
- 데이터: 검색 로그 테이블(사용자, 질문, 방식, 결과 조각 ID · 점수, 시각) + PostgreSQL 키워드 검색 확장 pg_trgm · 조각 본문 색인 → 버전 파일 0003. 원문은 이미 `notes.content`에 있음. (사용자 확인, 2026-11-10)
- 테스트: 검색 테스트는 PostgreSQL에서만 돈다(SQLite에는 pg_trgm이 없음 — 진짜로 쓸 검색을 시험하려고). (사용자 확인, 2026-11-10)
- 평가 세트: 질문 · 정답 조각은 사용자가 정하고 AI는 후보만 낸다. 공부 기록 내용이 들어가므로 레포에 올리지 않고 로컬에만 둔다. (사용자 확인, 2026-11-10)

## 결과 (AI 작성 — 구현 후)
- 1차 구현(2026-11-10):
  - 흐름: 검색창(`/records?q=`, `next/form`) → 서버 컴포넌트가 `GET /api/search` → 라우터(app/api/search.py)가 `Depends(get_searcher)`로 검색 방식을 받음 → 서비스(app/services/search_service.py)가 낱말 뽑기 → 검색 → 발췌 → `search_logs` 저장 → 결과 줄 → 누르면 `/records/{노트}?chunk={조각}#chunk-{조각}` → 노트 상세가 `GET /api/notes/{id}`의 원문에서 그 구간을 강조.
  - 검색 방식(app/search/): `Searcher` 약속 + `KeywordSearcher`(pg_trgm). 낱말마다 `content %> 낱말`(비슷함 0.6 이상, GIN 색인)으로 거르고 `word_similarity` 점수를 더해 순위. 조각 · 노트 둘 다 user_id 조건. 바꿀 때는 `get_searcher` 한 곳.
  - 낱말 뽑기: 글자 · 숫자 덩어리, 2글자 이상, 같은 낱말 하나로, 최대 10개. 검색어 200자 · 결과 5개 상한(app/config.py, 화면 lib/records.ts에도 200).
  - 실측(2026-11-10, 도커 PostgreSQL en_US.utf8): 조사가 붙어도 찾음("useEffect를" ↔ "useEffect는" 0.82), 띄어쓰기가 다르면 못 찾음("상태관리" ↔ "상태 관리" 0.4). 문장 "컴포넌트 상태를 바꾸면" → 낱말 3개가 맞은 조각이 1위.
  - 발췌 · 낱말 표시: 서버가 발췌(160자)와 원문에 실제 있던 낱말 모양(`matched_terms`)을 주고, 화면은 그 낱말을 문자열로 찾아 `<mark>`. 글자 위치를 주고받지 않아 파이썬 · 자바스크립트 글자 단위 차이가 없음.
  - 노트 상세 강조: 위치는 파이썬 코드 포인트 단위라 `Array.from(content)`로 잘라 맞춤(lib/text-range.ts, 이모지 뒤 조각으로 Playwright 확인).
  - 데이터: 버전 파일 0003 — pg_trgm 확장(PostgreSQL만) + `ix_chunks_content_trgm` + `search_logs`. 개발 DB 0002 → 0003 적용.
  - 평가: `app/search/evaluation.py`(채점 규칙) + `scripts/search_eval.py`(실행). 정답은 노트 제목 + 제목 경로로 적음(다시 올리면 조각 ID가 바뀌어서). tag별 비율(예: "다른낱말")도 냄. 세트 · 결과는 `backend/eval/`에 두고 `.gitignore`로 레포 밖.
  - 확인: pytest SQLite 172개 · PostgreSQL 178개 통과(test_search.py · test_search_eval.py 포함), Playwright 14개 · tsc · eslint · next build 통과. 실제 uvicorn + `next dev`(개발 DB)로 Next 프록시 거쳐 가져오기 → 검색 3종 · 위치 일치 · 결과 화면 · 노트 상세 강조 · 없는 노트 404 · 검색 로그 직접 실행, 확인용 계정은 끝나고 삭제(로그도 같이 지워짐).
- 1차 리뷰 반영(2026-11-10, 1차 [주의] → 사용자 판정: 주의 4 + 싼 제안 E · H · J 수정, 시간 상한 3초):
