# D-015 DB 구조 변경은 Alembic 버전 파일로 한다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 사용자가 골랐어요(2026-11-10).
무엇을: DB의 표(테이블) 모양을 바꿀 때마다 "무엇을 어떻게 바꿨는지"를 번호 붙은 파일로 남기고, 명령 한 줄로 DB에 적용해요. 집 공사 기록부처럼, 어느 DB든 기록부를 처음부터 따라 하면 같은 모양이 돼요. 서버는 더 이상 표를 직접 만들지 않고, 켜질 때 "DB가 최신 기록까지 적용됐는지"만 확인해요.
왜: SQLAlchemy를 쓰고 있으니 같은 계열 도구인 Alembic으로 간다. 모델 변경이 버전 파일로 남아 다른 환경(테스트 · 배포)에서 같은 순서로 재현된다. (사용자 확인)

## 개발자 상세

### 상황
- 지금까지 서버 시작 때 `create_all`로 없는 테이블만 만들었다. 기존 테이블에 컬럼을 추가하는 변경은 반영되지 않는다(Q-016).
- 2주차(F-003)에 `chunks.embedding`(pgvector) 컬럼과 확장 설치가 필요하다.

### 후보
| | A. Alembic | B. `create_all` + 손으로 SQL | C. DB를 지우고 다시 만들기 |
|---|---|---|---|
| 방식 | 변경마다 버전 파일, `upgrade` 한 줄로 적용 | 컬럼을 바꿀 때마다 SQL 직접 실행 | 구조가 바뀌면 볼륨 삭제 |
| 장점 | SQLAlchemy 공식 도구, 이력이 코드로 남음, 배포 DB에도 같은 방식 | 새 패키지 없음 | 가장 단순 |
| 단점 | 패키지 추가, 처음 설정 필요 | 로컬 · 배포 DB가 어긋나기 쉬움 | 가져온 기록이 사라짐, 배포 후엔 못 씀 |

### 결정
- A. Alembic. 설정은 `backend/alembic.ini`, 실행 환경은 `backend/migrations/env.py`, 버전 파일은 `backend/migrations/versions/`.
- DB 주소는 `alembic.ini`에 적지 않고 환경변수 `DATABASE_URL`에서 읽는다.
- 첫 버전 `0001`은 그때까지의 users · notes · chunks 그대로다.
- 서버는 테이블을 만들지 않는다. 시작할 때 DB 버전이 최신인지 확인하고, 아니면 실행할 명령을 적은 오류로 멈춘다(`app/db/schema_version.py`). DB에 연결이 안 될 때 · DB가 코드보다 앞설 때(코드가 모르는 버전)는 각각 다른 안내를 낸다. 오류 문구에 DB 주소는 넣지 않는다.
- 테스트는 속도를 위해 계속 `create_all`을 쓴다. 대신 "버전 파일을 다 적용한 DB = 모델"인지 확인하는 테스트를 둔다(`tests/test_migrations.py`). 모델만 고치고 버전 파일을 안 만들면 이 테스트가 실패한다.

### 결과로 생기는 제약
- 모델(`app/db/models.py`)을 바꾸면 버전 파일을 같이 만든다: `alembic revision --autogenerate --rev-id 000N -m "영문 설명"` → 내용을 읽고 고친 뒤 커밋.
- DB를 새로 만들거나 코드를 받은 뒤에는 `alembic upgrade head`를 실행해야 서버가 뜬다.
- 전에 `create_all`로 만든 DB는 처음 한 번 `alembic stamp 0001`(구조는 그대로 두고 "0001까지 적용됨"만 기록).
- `alembic.ini`와 `script.py.mako`는 영문만 쓴다. 버전 파일 설명의 첫 줄도 영문(한국어 Windows에서 cp949로 읽히거나 찍혀서 깨짐, T-003).
- 배포할 때 "서버를 켜기 전에 `upgrade head`"를 넣는 방법은 배포 위치(Q-012)와 함께 정한다.

### 이 결정을 바꿔야 하는 조건
- 버전 파일이 갈라져(브랜치) 혼자 쓰는 프로젝트에 비해 관리가 과해질 때. (지금은 최신 버전이 하나인지 테스트로 확인)
