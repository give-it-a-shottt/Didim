## 지적
- [주의] [확실] 샘플 세션이 GET으로 DB에 쓰는 길이 하나 남아 있다. `GET /api/search`는 검색마다 `search_service._save_log`로 SearchLog를 저장 · commit하는데 BLOCKED_READS에 없다. 로그인 없는 누구나 `POST /api/demo/session` 한 번 뒤 `GET /api/search?q=…`를 반복해 샘플 사용자 이름으로 search_logs를 끝없이 쌓을 수 있다(상한 · 속도 제한 없음, 방문자 검색어가 DB에 남음). sample_guard 문서와 test_get_routes_snapshot의 "GET이 저장하면 BLOCKED_READS에 넣는다"와도 어긋난다. 전엔 구글 로그인이 필요했다. — app/api/sample_guard.py BLOCKED_READS, app/services/search_service.py search_records · _save_log(50~68행), app/api/search.py — 확인한 범위: diff의 sample_guard.py · test_sample_guard.py, search.py 전체, search_service.py 28~72행, services의 commit · add grep(메인도 search_service.py에서 다시 확인) — 고치는 방법: 샘플이면 _save_log를 건너뛰거나, "/api/search"를 BLOCKED_READS에 넣는다. 어느 쪽이든 "샘플 검색 뒤 search_logs 0줄" 테스트.
- [주의] [확실] 시드가 공개 샘플 계정의 하루 AI 상한을 SAMPLE_DAILY_LIMIT = 10,000으로 둔 채 끝난다. 샘플의 AI 호출을 막는 건 SampleReadOnlyGuard 하나뿐이라, 나중에 AI를 부르는 GET이 생기거나 가드에 빈틈이 생기면 누구나 여는 계정에 사실상 상한이 없다(설계 원칙 4 이중 방어 없음). — app/services/sample_seed.py SAMPLE_DAILY_LIMIT · reset_sample_user · seed_sample — 확인한 범위: diff의 sample_seed.py, models.py daily_limit, usage_service.py 73행 — 고치는 방법: seed_sample 끝에서 샘플 daily_limit을 0으로 되돌리고 테스트로 고정.
- [제안] [추정] `POST /api/demo/session`에 요청 출처 확인이 없다. 다른 사이트의 최상위 form POST로 로그인한 사람이 로그아웃되고 샘플 세션으로 바뀔 수 있다(로그인 CSRF). 샘플은 쓰기가 막혀 남는 피해는 강제 로그아웃 정도. — app/api/demo.py open_sample_session — 확인한 범위: diff의 demo.py, backend · frontend의 Origin · CSRF · Sec-Fetch grep(없음), next.config rewrites 본문과 실제 브라우저 동작은 확인 안 함 — 확실해지려면: 다른 출처 페이지에서 form POST를 보내 쿠키가 바뀌는지 직접 본다. — 고치는 방법: demo/session(과 logout)에서 Sec-Fetch-Site가 same-origin이 아니거나 Origin이 사이트 주소가 아니면 403. 또는 프론트 fetch에만 붙는 사용자 지정 헤더 요구.
- [제안] [추정] 샘플 여부를 토큰 표시만으로 정하고, 그 uid가 정말 샘플 사용자인지는 맞춰 보지 않는다. 시드가 샘플 사용자를 다시 만들 때 id를 다시 쓰는 DB(SQLite 등)에서는 옛 샘플 토큰 uid가 다른 사용자를 가리킬 수 있다(PostgreSQL은 다시 안 씀). — app/api/deps.py get_current_user, app/api/sample_guard.py _is_sample — 확인한 범위: deps.py 전체, auth_service.py 60~119행, diff의 reset_sample_user. 배포 DB 종류 · SQLite AUTOINCREMENT는 확인 안 함 — 확실해지려면: 배포 DB가 PostgreSQL로 고정인지, 개발 SQLite users PK가 AUTOINCREMENT인지 확인. — 고치는 방법: get_current_user에서 토큰에 sample 표시가 있는데 user.google_sub != SAMPLE_GOOGLE_SUB면 401(추가 쿼리 없음).
- [제안] [확실] 성능: 공개 `/report`는 방문마다 no-store로 백엔드를 부르고, `list_summaries`는 요청마다 run-*.json 전부를 읽고 파싱한 뒤 10개로 자른다. 수치는 평가 · 배포 때만 바뀌는데 검색 노출 페이지라 반복 호출이 그대로 파일 I/O. — frontend/src/lib/backend.ts fetchBackendPublic, lib/report-data.ts, backend/app/services/eval_report.py list_summaries, app/api/report.py — 확인한 범위: diff — 고치는 방법: 프론트 캐시(use cache + cacheLife 또는 revalidate), 백엔드는 앞쪽 일부만 읽거나 mtime 기준 메모리 캐시.
