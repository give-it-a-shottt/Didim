## 지적

- [신규] [위험] [확실] 경로 끝에 `%0A`를 붙이면 `ImportUploadGuard`를 비켜 가서, 1차 지적 1의 문제(머리말 없는 요청을 크기 제한 없이 · 로그인 확인 전에 받음)가 그대로 다시 열린다. 가드는 `scope["path"]`를 `"/api/notes/import"`와 문자열로 정확히 비교하는데(upload_limit.py:31), uvicorn은 `%0A`를 줄바꿈으로 디코딩하고(httptools_impl.py:259-263), starlette 라우터는 경로 정규식을 `^…$` + `match`로 검사해서(starlette routing.py:167 · :255) 파이썬 `$`가 끝 줄바꿈 앞에서도 맞기 때문에 `"/api/notes/import\n"`이 가져오기 엔드포인트로 들어간다. 실측: (1) 실제 앱에 쿠키 없이 머리말 없는 30MB → 정상 경로는 401 · 0바이트, `\n` 경로는 30MB를 끝까지 읽은 뒤 401. (2) 실제 uvicorn(httptools)으로 띄워 `POST /api/notes/import%0A`(대문자 · 소문자 둘 다)에 1MB만 보냄 → 응답 없이 본문을 계속 기다림(정상 경로는 바로 401). 로그인한 사용자라면 이 경로로 정상 가져오기도 되므로 21MB 상한 없이 올릴 수 있다. — 위치: backend/app/api/upload_limit.py:19, :31 — 확인한 범위: scratchpad 스크립트로 실제 앱(ASGI 직접 호출)과 실제 uvicorn 서버(127.0.0.1 임시 포트, SQLite 임시 파일)에서 측정. Next.js 프록시(rewrites)가 `%0A`를 그대로 백엔드에 넘기는지는 확인 안 함(백엔드에 직접 닿는 경로가 있으면 그대로 해당). 같은 비교 방식 때문에 uvicorn에 `--root-path`를 주는 배포에서는 모든 요청이 가드를 비켜 감(uvicorn이 `scope["path"]` 앞에 root_path를 붙이고 라우터는 `get_route_path`로 떼어 냄) — 지금 실행 명령에는 root-path가 없음. — 고치는 방법: (a) 가드 맨 앞에서 경로에 제어 문자(`\x00`~`\x1f`, `\x7f`)가 있으면 경로와 상관없이 본문을 읽지 않고 400으로 끝낸다. (b) 비교는 라우터와 같은 기준인 `starlette._utils.get_route_path(scope)`(공개 API가 아니면 같은 로직을 작은 함수로)로 한다. 더 튼튼하게 하려면 (c) 바이트 세기를 이 경로뿐 아니라 모든 요청에 걸고(다른 경로는 더 작은 상한) 쿠키 확인만 이 경로에 둔다. 테스트: `POST /api/notes/import%0A`(쿠키 없음, 머리말 없음) → 본문 0바이트 읽고 400 또는 401, 그리고 root_path를 준 scope에서도 가드가 걸리는지.

- [신규] [주의] [확실] 조각 상한(2,000)을 나누기가 다 끝난 뒤에 확인해서, 상한을 훨씬 넘는 파일도 끝까지 나누며 메모리 · CPU를 쓴다. `_sections`가 구역마다 제목 경로 문자열을 새로 만들고(chunking.py:58-62) `split_markdown`이 전부 `ChunkDraft`로 만든 다음(:127-154) `import_service.py:117`에서 개수를 본다. 경로는 이제 최대 418자로 막혔지만 구역 수만큼 복사된다. 실측(1MB, 300자 제목 2단계 + `### a\nb\n` 반복): 조각 130,996개, 읽기 0.26초 + 나누기 0.77초(tracemalloc 없이), 나누기 최대 메모리 약 212MB(제목이 ASCII · 한글), 이모지 제목이면 약 316MB(tracemalloc 기준). 결국 실패로 끝날 파일 하나가 이만큼 쓰고, 요청 하나에 20개면 GIL을 잡은 순수 파이썬 계산 약 20초가 이어진다. 동시에 여러 요청이면 메모리가 요청 수만큼 늘어난다. 로그인한 사용자만 가능. — 위치: backend/app/services/chunking.py:50-65, :127-154, backend/app/services/import_service.py:113-119 — 확인한 범위: 레포 venv에서 `read_markdown_file` · `split_markdown`만 실행해 시간 · 메모리 측정. 20개 요청 시간과 동시 요청 메모리는 1개 측정값으로 외삽, DB 저장은 상한에서 막혀 해당 없음. 상한 값 자체는 사용자 결정이라 보지 않음. — 고치는 방법: `split_markdown(content, max_chunks=MAX_CHUNKS_PER_NOTE)`처럼 상한을 넘겨 받아, 조각이 상한을 넘는 순간 멈추고(예: `TooManyChunksError`를 올리거나 표시값을 돌려줌) 서비스가 그 파일만 실패로 돌린다. `_sections`를 제너레이터로 바꾸면 멈춘 뒤의 구역 경로도 만들지 않는다. 테스트: 위 1MB 파일이 실패로 끝나는 시간이 2,001조각 파일(실측 0.009초)과 비슷한 수준인지, 또는 만들어진 `ChunkDraft` 수가 상한 + 1을 넘지 않는지.

- [제안] [확실] 이름만 맞는 가짜 세션 쿠키(`didim_session=x`, 값이 비어도 됨)를 붙이면 로그인 없이 21MB까지 본문을 받게 한 뒤에야 401이 나간다. 1차 지적 6은 "쿠키가 없을 때"만 해소됨. 메모리는 이제 요청당 약 21MB로 묶여서 1차보다 영향은 작다. — 위치: backend/app/api/upload_limit.py:36 — 확인한 범위: 실제 앱에 ASGI 요청을 넣어 측정(가짜 쿠키 + 머리말 없는 30MB → 21.0MB 읽고 413, 상한 안이면 다 읽은 뒤 401). `verify_session_token`(auth_service.py:127-135)이 DB 없이 서명 · 만료만 보는 순수 함수인지 읽어 확인. — 고치는 방법: 가드에서 쿠키 값으로 `verify_session_token(token, settings.session_secret)`을 불러 None이면 본문을 읽기 전에 401(문구는 deps.py와 같게). 사용자 존재 확인(DB)은 지금처럼 `get_current_user`에 둔다. 설정을 못 읽으면(SessionConfigError) 지금처럼 그대로 통과시켜 기존 500 처리에 맡긴다.
