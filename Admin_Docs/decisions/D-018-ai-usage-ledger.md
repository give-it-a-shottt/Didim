# D-018 AI 사용량은 모든 기능이 같이 쓰는 표 하나로 센다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 사용자가 골랐어요(2026-11-11).
무엇을: 퀴즈 · 카드 후보 · 자소서 · 면접처럼 AI를 부르는 기능이 쓴 양을 표 하나(`ai_usage_logs`)에 요청마다 한 줄씩 남기고, 하루 상한(30)은 이 표로 세요. 하루는 한국 시간 0시에 다시 시작해요.
왜: F-004 완료 기준 6(하루 AI 호출 30회 상한)에 사용량 기록이 필요한데, F-001에서 2주차에 하기로 한 사용량 기록이 아직 없었어요. 기능마다 따로 세면 다음 기능마다 세는 방법을 또 만들어야 해서, 처음부터 공용 표로 해요(사용자, 2026-11-11).

## 개발자 상세

### 후보
| | A. 공용 사용량 표 (요청마다 한 줄) | B. 기능별 로그로 세기 (`quiz_generation_logs`) | C. 날짜별 카운터 표 (`user_id, 날짜, calls`) |
|---|---|---|---|
| 장점 | 기능이 늘어도 세는 곳 하나, 실패 이유 · 기능별 내역이 남아 평가 로그(원칙 5) · 사용량 화면(7주차)에 그대로 씀 | 지금 표 하나 덜 만듦 | 오늘 사용량 조회가 가장 빠름 |
| 단점 | 표 하나 추가, 오늘 사용량을 합계로 구함 | 다음 기능마다 세는 방법을 따로 만들고 합쳐야 함 | 내역 · 실패 이유가 남지 않음 |

### 결정 (사용자 확인, 2026-11-11 — 선택지로 받음)
- A. 표 `ai_usage_logs`: `user_id`(FK `ON DELETE CASCADE`), `feature`(예: `quiz_generate`), `calls`, `prompt_tokens`, `completion_tokens`, `outcome`(ok · invalid_output · rate_limited · unavailable 등 오류 종류만), `created_at`. 색인 (`user_id`, `created_at`). 버전 파일 0004에서 F-004 표들과 같이 만든다.
- 세는 단위: 실제 AI 호출 수(F-014 `usage.calls` — 연결 재시도 · 형식 재요청까지 포함, 실패한 호출도 셈). 토큰은 기록만 하고 상한은 아직 두지 않는다.
- 하루 기준: 한국 시간(Asia/Seoul) 0시. 저장은 UTC, "오늘 0시"를 한국 시간으로 계산해 UTC로 바꿔 비교한다. F-004 '오늘 복습'의 '오늘'도 같은 함수를 쓴다.
- 확인 시점: AI를 부르기 전에 `오늘 SUM(calls) < users.daily_limit`이면 시작하고, 끝난 뒤(성공 · 실패 모두) 실제 사용량을 한 줄 기록한다. 상한에 걸리면 AI를 부르지 않고 남은 사용량을 안내한다.
- `quiz_generation_logs`는 평가용 숫자(요청 · 남긴 · 버린 수와 이유)만 두고, 호출 · 토큰은 이 표에서 본다(F-004 데이터 설계에서 바뀐 부분).
- 기록에는 보낸 내용 · 받은 내용 · API 키를 넣지 않는다(F-014 오류 문구 규칙과 같음).

### 결과로 생기는 제약
- 동시에 들어온 요청이나 한 요청 안의 재시도(최대 4회) 때문에 하루 30을 조금 넘을 수 있다. AI를 부르는 동안(최대 180초) DB를 잠그지 않기 위해 받아들인 것(사용자 확인).
- 사용량 기록 저장이 실패하면 그 호출은 세지지 않는다. 결과는 사용자에게 돌려주고 실패를 로그로 남긴다(검색 로그와 같은 방식 — 구현 때 테스트로 확인).
- F-001 계획의 "7주차 사용량 제한" 중 호출 수 상한은 3주차(F-004)로 당겨진다. 사용량 화면 · 토큰 상한은 7주차 그대로.

### 이 결정을 바꿔야 하는 조건
- 상한을 넘는 일이 실제로 문제가 될 때(공개 배포 · 유료 API) → 미리 예약하고 정산하는 방식으로 바꾼다.
- 표가 커져 오늘 합계 조회가 느려질 때 → 날짜별 카운터를 함께 둔다.
