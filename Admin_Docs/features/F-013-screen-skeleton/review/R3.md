## 지적 (있을 때)
- [신규] [제안] [추정] 저장소를 쓸 수 없거나 쓰기가 실패하면 화면이 다시 마운트될 때 접힌 상태가 펼침으로 되돌아간다 — frontend/src/components/sidebar-toggle.tsx 의 useLayoutEffect(`storedCollapsed() !== isCollapsed()` 이면 `applyCollapsed(storedCollapsed())`) — 확인한 범위: 패킷의 sidebar-toggle.tsx 전문 · sidebar-state.ts · layout.tsx. 직접 연 파일 없음.
  - 상황: localStorage 접근이 막힌 브라우저(또는 setItem이 용량 초과로 실패)에서 사용자가 접으면 `<html>` 속성만 붙고 저장은 실패한다(toggle의 catch). 이후 SidebarToggle이 다시 마운트되면(개발 모드 Strict Mode, 또는 사이드바가 없는 화면에 갔다가 돌아오는 경우) `storedCollapsed()`는 catch 때문에 false, `isCollapsed()`는 true라서 불일치로 보고 펼침으로 되돌린다. "기억만 못 할 뿐 접기 · 펴기는 된다"는 주석의 의도와 어긋난다. 같은 앱 화면 사이 이동에서는 레이아웃이 유지되면 마운트가 다시 일어나지 않으므로 영향은 작다. 사이드바가 다시 마운트되는 경로가 있는지는 패킷만으로 알 수 없어 [추정]이다.
  - [확실]로 바꾸려면: 저장소를 막은 상태(Playwright에서 addInitScript로 localStorage 접근을 throw하게 함)에서 접은 뒤 사이드바가 없는 화면을 거쳐 돌아오기(또는 개발 서버에서 Strict Mode 재마운트)로 폭이 240으로 돌아가는지 본다.
  - 고치는 방법: `storedCollapsed()`가 읽기 실패와 "저장된 값 없음"을 구분하게(예: 실패하면 null) 하고, null이면 useLayoutEffect에서 속성을 건드리지 않는다.
- [신규] [제안] [확실] 저장소를 못 쓰는 경우와 화면 이동 뒤 상태를 확인하는 테스트가 없다 — frontend/tests/sidebar.spec.ts — 확인한 범위: 패킷의 sidebar.spec.ts 전문.
  - 지금 2개 테스트는 정상 경로(접기 · 펴기 · 새로 고침 · 링크 이동)와 "늘 접힘 + 버튼 없음"만 다룬다. 빠진 것: (a) localStorage가 throw할 때 접기 · 펴기가 동작하는지(init 스크립트와 toggle의 catch 분기), (b) 자소서 탭에서 다른 탭으로 클라이언트 이동했을 때 사용자 선택(펼침/접힘)대로 돌아오는지. 후자는 `:has()`와 숨겨진 앞 화면(display: none) 예외가 얽힌 부분이다. 둘째 테스트는 자소서 탭을 주소로 직접 열 뿐이다.
  - 고치는 방법: (a) `context.addInitScript`로 `Storage.prototype.getItem/setItem`이 throw하게 만든 뒤 접기 → 폭 56, 펴기 → 폭 240 확인. (b) 펼침 상태에서 `/applications/910/draft` 링크 이동 → 56, 같은 공고의 다른 탭 링크 이동 → 240, 접힘 상태에서도 같은 순서로 56 → 56 확인.
  - 참고(추정, 지적 아님 — 근거는 재현 필요): 첫 테스트는 `goto` 직후 바로 버튼을 누른다. 개발 서버에서 하이드레이션이 끝나기 전에 누르면 onClick이 없어 클릭이 사라질 수 있다. 지금은 88개 통과라 문제로 드러나지 않았다.
