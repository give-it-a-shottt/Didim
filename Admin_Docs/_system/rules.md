# 작성 규칙

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과]
무엇을: Admin_Docs를 쓰고 고칠 때 지키는 약속이에요. 코드는 AI가 짜고, 사용자는 설계자로서 구조를 정하고 결과를 판정해요. Admin_Docs는 "코드가 어떻게 생겼고 왜 그런지"만 다루고, 디자인 원본은 레포 루트 [didim-design.md](../../didim-design.md)에 있어요.
왜: 면접에서 이 프로젝트의 구조와 설계 이유를 AI 없이 설명하려고요.

## 개발자 상세

### 절대 규칙
1. **사용자 작성 칸은 AI가 내용을 지어내지 않는다.** 대상은 START_HERE의 서비스 소개, F-00X의 설계 의도, 리뷰 SUMMARY의 최종 판정, 면접 예상 질문의 답, 열린 질문 중 사용자가 정할 질문의 답이에요. 비어 있으면 질문 1~2개로 묻고, 사용자의 말을 아래 문장 정리사 절차로 다듬어 승인받은 문장만 적어요. 칸 옆에 (사용자 확인)이라고 표시해요.
2. **민감 정보 금지**: 아래 목록은 어떤 문서에도 쓰지 않고 이름만 적어요.
3. **Admin_Docs는 레포에 커밋한다.** .gitignore에 넣지 않아요.
4. **모든 문서는 2층 구조**로 써요. 위층은 한눈에 보기(코드 몰라도 OK), 아래층은 개발자 상세예요. STATUS.md와 OPEN_QUESTIONS.md는 표 중심이라 한눈에 보기 한 층만 둬요.
5. **길이**: 쉬운 내용은 짧게, 어려운 내용은 풀어 쓰되 한 항목은 5줄을 넘기지 않아요. 위층에 전문 용어를 쓰면 [glossary.md](glossary.md)에 추가해요.
6. **표기**
   - 문서 상태: [통과] [주의] [위험]
   - 지적 등급: [위험] [주의] [제안], 2차 이상 리뷰에서 새로 생긴 지적은 등급 앞에 [신규]
   - 지적 확신: [확실] [추정]
   - 기능 진행 상태(STATUS): [됨] [일부] [다음]
   - 질문 상태(OPEN_QUESTIONS): [열림] [닫힘]
7. **이모지**는 💡 ❓ ⚠️ 세 개만 써요.
8. **문서와 코드가 다르면** 코드에 맞춰 문서를 고치기 전에, 어느 쪽이 의도인지 사용자에게 먼저 물어요. 지금 답을 못 받으면 [OPEN_QUESTIONS.md](../OPEN_QUESTIONS.md)에 적어 둬요.
9. **디자인은 다루지 않는다.** 디자인 내용(색 값, 무드, 벤치마킹, 컴포넌트 모양 등)을 Admin_Docs에 쓰지 않고, 리뷰어도 디자인 · 접근성 · 색 대비를 지적하지 않아요. 원본은 [didim-design.md](../../didim-design.md)이고, 평가는 사용자가 직접 해요. 열린 질문에도 디자인 질문은 적지 않아요.
10. **토큰 절약**: 리뷰어는 레포 전체를 탐색하지 않고, 메인이 만든 리뷰 패킷을 기준으로 봐요.
11. **사용자가 정할 것은 추측으로 정하지 않는다.** 작업 중 그런 선택을 만나면 OPEN_QUESTIONS.md에 적고, 작업을 계속할 수 있으면 가장 되돌리기 쉬운 쪽으로 임시 진행한 뒤 그 사실을 질문에 함께 적어요.
12. **STATUS의 [됨]은 확인 방법이 있을 때만** 써요. 없으면 [일부]예요.

### 문장 정리사
사용자가 편하게 말한 내용을 문서에 남길 문장으로 다듬어요. 사용자 작성 칸에만 써요.

절차
1. 사용자가 편하게 말해요.
2. 다듬은 문장을 "❓ 이렇게 남길까요?"와 함께 보여 줘요.
3. OK를 받으면 저장하고 (사용자 확인)을 붙여요. 고쳐 달라고 하면 반영해서 다시 보여 주고, OK 전에는 저장하지 않아요.
4. 원문(처음 한 말)은 어디에도 저장하지 않아요. 승인된 문장만 남겨요.

정리사 규칙
- 사용자가 말하지 않은 내용·이유·예시를 덧붙이지 않아요.
- 판단의 세기를 바꾸지 않아요("괜찮은 것 같다" → "적절하다" 금지, "아마" → "반드시" 금지).
- 사용자가 쓰지 않은 전문 용어로 바꾸지 않아요. 면접에서 그대로 말할 수 있는 문장이어야 해요.
- 맞춤법·어순·군더더기·중복만 정리하고, 여러 말이 섞이면 항목별로 나눠요.
- 애매하거나 빠진 부분은 지어내지 않고 ❓로 한 가지만 되물어요. 여러 칸은 칸별로 따로 승인받아요.

### 리뷰 범위
기준은 "기능이냐"가 아니라 "코드가 바뀌었냐"예요. 같은 표가 레포 루트 [CLAUDE.md](../../CLAUDE.md)에도 있어서, 스킬을 부르지 않아도 지켜져요.

| 작업 | 리뷰 |
|---|---|
| 기능 추가·변경 | R1~R4 |
| 버그 수정·설정값·문구 | R1, R3, R4 |
| 리팩터링 | R1, R3 (동작이 그대로인지 테스트로 확인) |
| 패키지 추가·업그레이드 | R2 |
| 문서만 (Admin_Docs, README, 주석) | 리뷰 없음, 민감 정보만 확인 |

- 여러 종류가 섞이면 해당하는 리뷰어를 합쳐요. 판정 결과는 사용자에게 한 줄로 알려요.
- 리뷰 없음인 작업은 문서 갱신·리뷰·판정 단계를 건너뛰고, 민감 정보 확인 결과만 한 줄로 알려요.

### 리뷰어 4인과 리뷰 패킷
| 리뷰어 | 담당 모델 | 체크리스트 |
|---|---|---|
| R1 구조·가독성 | Sonnet | [R1](reviewers/R1-structure-readability.md) |
| R2 보안·성능 | Opus | [R2](reviewers/R2-security-performance.md) |
| R3 예외 처리·테스트 | Sonnet | [R3](reviewers/R3-errors-tests.md) |
| R4 설계 의도·API 계약 | Sonnet | [R4](reviewers/R4-intent-api.md) |

- 메인이 리뷰 패킷(작업 요약 · 바뀐 파일과 diff · 설계 의도 · 관련 overview · D-00X 요약 · 테스트를 한 번 돌린 결과)을 만들어 넘겨요. 리뷰어는 레포 전체를 뒤지지 않고, 테스트를 다시 돌리지 않아요. 패킷은 파일로 남기지 않아요.
- 리뷰어마다 서브에이전트 하나, 다른 리뷰어 결과는 보지 않아요. 가장 가벼운 모델(Haiku)은 쓰지 않아요. 지정 모델을 못 쓰면 SUMMARY에 적어요.
- 결과는 항목마다 한 줄 "항목 → 확인한 위치 → 결과"로 짧게 써요. 지적마다 [확실]/[추정]과 확인한 범위를 붙여요.
- 열린 질문의 임시 처리 때문에 생긴 문제는 지적 대신 "Q-00X 임시 처리와 관련"이라고 적어요.
- 리뷰가 끝나면 REVIEW_LOG, STATUS, OPEN_QUESTIONS를 정리해요.
- 같은 기능을 다시 리뷰하면(2차 이상) 메인이 이전 회차 R{n}.md와 비교해 새 지적에 [신규]를 붙이고, 애매하면 [신규]로 둬요. R{n}.md는 최신 회차로 덮어쓰고 이전 회차는 git 기록으로 남겨요.

### 민감 정보 금지 목록
- API 키·토큰·비밀번호와 `.env` 파일의 값. 예를 들어 "환경변수 `LLM_API_KEY` 사용"처럼 이름만 써요.
- DB 접속 정보(`DATABASE_URL`의 값, 호스트·계정)
- 개인정보: 실명, 연락처, 이메일, 주소. 사람은 "사용자", "팀원" 같은 역할로만 불러요.
- 에러 로그를 옮길 때는 키·토큰·URL 쿼리의 비밀값을 지워요.

### 확신 표시 (지적마다)
- [확실]: 해당 코드를 직접 읽고(패킷 diff 또는 직접 연 파일) 문제를 확인했어요. 테스트 실패처럼 결과로 드러난 것도 [확실]이에요.
- [추정]: 일부만 봤거나, 관련 파일을 안 열었거나, 실행해 봐야 알 수 있어요. "무엇을 확인하면 [확실]이 되는지"를 한 줄 적어요.
- 확인한 범위: 실제로 본 것을 짧게 써요. 예) "diff의 auth_service.py만 봄, 라우터는 안 봄"

### STATUS 상태 기준
- [됨]: 완료 기준을 모두 충족했고 확인 방법(테스트 통과, 직접 실행, 리뷰 [통과] 중 하나 이상)이 있어요. 리뷰가 [위험]이면 [됨]이 될 수 없어요.
- [일부]: 시작했거나 일부만 되거나, 됐지만 확인 방법이 없어요. 무엇이 빠졌는지 적어요.
- [다음]: 할 예정이지만 시작 전이에요.
- 확인 방법 칸은 실제로 한 확인만 적어요("테스트 {파일} 통과(날짜)"). 리뷰 [통과]뿐이면 "실행 확인 없음"을 함께 적어요.

### 질문 규칙
- 누가 정해야 하나: 사용자(설계 결정) · 공부(이해하고 싶은 원리) · 확인 필요(AI가 더 보면 풀리는 것)
- 사용자가 말한 질문은 한 줄로 정리해 한 번 확인받고 추가해요. AI가 올린 질문은 바로 추가하고 작업 보고 때 알려요.
- 답이 나오면 알맞은 문서(D-00X · T-00X · overview · feature.md)로 옮기고 [닫힘]으로 옮겨요. 답 내용은 OPEN_QUESTIONS에 다시 쓰지 않아요.
- 임시 처리와 다른 답이 나오면 코드를 바꿔야 한다고 알리고, 바꾼 뒤 리뷰 범위를 판정해요.

### 범위 밖
- ⚠️ 디자인(색 · 간격 · 폰트 · 컴포넌트 모양 · 반응형 레이아웃 · 접근성 · 색 대비)은 검수하지 않아요. 사용자가 직접 평가해요.
- ⚠️ 배포·서버 인프라·CI(배포 설정 파일, `.github/workflows/`)는 검수하지 않아요. 실제 배포·운영을 시작하면 R5 배포·운영 리뷰어(환경 분리, 로그, 모니터링, 롤백 방법)를 추가해요.
- `eval/` 아래 가상 데이터(카드 · 공고 · 정답표)는 코드가 아니라 시험지예요. 리뷰하지 않고, 바꾸면 D-005와 평가 리포트에 날짜를 남겨요.

### 번호와 파일 이름
- 결정 `decisions/D-00X-영문-제목.md` (결정 1개 = 파일 1개)
- 기능 `features/F-00X-영문-제목/feature.md`, 리뷰 `features/F-00X-영문-제목/review/R1.md ~ R4.md, SUMMARY.md`
- 기능의 후속 수정 리뷰는 `review/fix-0N-제목/`에 따로 둬요(예: F-002 fix-01-duplicate).
- 트러블 `troubleshooting/T-00X-영문-제목.md`, 목록은 [INDEX.md](../troubleshooting/INDEX.md)
- 리뷰 기록 [features/REVIEW_LOG.md](../features/REVIEW_LOG.md)
- 문서 안에서 다른 문서·코드 파일을 가리킬 때는 상대 경로 마크다운 링크로 써요(VS Code에서 Ctrl+클릭으로 열려요).
