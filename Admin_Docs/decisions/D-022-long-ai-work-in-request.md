# D-022 AI를 오래 부르는 처리는 요청 한 번 + 180초 상한으로 유지(백그라운드 작업 안 씀)

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 사용자가 골랐어요(2026-11-13, Q-008).
무엇을: 퀴즈 · 카드 후보 · 공고 분석(뒤에 자소서도)은 지금처럼 버튼을 누르면 요청 한 번 안에서 AI를 부르고, 최대 180초를 기다려요. 따로 작업 줄(큐) · 워커 · 상태 물어보기(폴링)는 만들지 않아요. 비유하면 창구에서 바로 처리하는 방식이고, 번호표를 받고 나중에 찾으러 오는 방식은 쓰지 않아요.
왜: 혼자 쓰는 포트폴리오라(Q-019) 지금 방식으로 충분하고, 남은 주차를 기능에 쓰려고요. 느린 시간대에는 180초를 넘겨 "다시 시도해 주세요"가 날 수 있어요(T-006).

## 개발자 상세
### 상황
- AI 호출은 동기 엔드포인트 + `anyio.from_thread.run`, 전체 180초 상한(F-014), 사용자당 AI 작업 1개(D-020), 프록시 상한 200초(T-005).
- F-007 평가(2026-11-13)에서 EXAONE 무료 API가 느린 시간대에 180초 초과 · 429가 났다.

### 후보
| 후보 | 장점 | 단점 |
|---|---|---|
| A. 지금처럼 요청 한 번 (선택) | 구조가 단순, 이미 테스트됨, 남은 시간을 기능에 씀 | 180초 상한, 요청이 스레드를 붙잡음, 느린 날 실패 |
| B. 백그라운드 작업 + 폴링 | 상한 없이 오래 걸려도 됨, 화면을 닫아도 계속 | 작업 표 · 워커 · 기존 3기능 변경, 1주 가까이 |
| C. 스트리밍 | 글자가 바로 보임 | JSON 결과는 다 받아야 검사 가능, 자소서는 근거 검사(D-003) 전에 보임 |

### 결정
- A. 새 AI 기능(F-008 자소서 · F-009 면접)도 같은 방식(요청 한 번 · 선점 · 180초)으로 만든다.

### 결과로 생기는 제약
- 한 요청에 묶는 AI 작업은 180초 안에 끝나야 한다 — 길면 F-007처럼 요청을 나눈다.
- 서버 작업 스레드 수가 동시에 AI를 기다릴 수 있는 사람 수의 상한이다.

### 이 결정을 바꿔야 하는 조건
- 공개 배포로 여러 사람이 동시에 쓰게 되거나(Q-012), 자소서처럼 한 번에 180초를 넘는 작업이 꼭 필요해지면 B를 다시 본다(그때 D-020도 큐 기준으로 다시 정함).
