### 보안·백엔드
- 인증 · 권한(OAuth state) → auth_service.py `create_notion_state_token` · `verify_notion_state_token`(패킷 diff 333~354), api/notion.py `notion_connect` · `notion_callback`(135~220) → 정상. 서명 + 용도(`notion_state`, 구글 state와 따로) + 만료 10분 + 쿼리 state = 쿠키 state(ASCII 확인 뒤 compare_digest) + 담긴 uid = 지금 로그인한 사용자. 쿠키 httponly · SameSite=Lax · secure 설정값 · path `/api/notion`, 돌아갈 때 쿠키 삭제. 공격자가 자기 코드 + state로 만든 콜백 링크는 피해자 쿠키와 맞지 않아 거절됨.
- 인증 · 권한(비로그인) → api/notion.py `_user_or_none` · `_login_redirect`(109~124) → 정상. connect · callback은 401만 None으로 바꿔 /login으로 보내고, 그 밖 예외는 그대로 올림. 나머지 4개 API는 `get_current_user` 필수. 참고: callback은 `error` 쿼리를 state 확인보다 먼저 보므로 외부 링크로 '연결을 취소했어요' 안내 + state 쿠키 삭제가 일어날 수 있으나 상태 변경 · 데이터 노출이 없어 지적하지 않음.
- 인증 · 권한(사용자 분리, D-004) → notion_service.py `_get_connection` · `claim_import` · `release_import` · `disconnect`(DELETE where user_id) · `list_pages`(Note.user_id + IN) · `_Importer._existing_by_page` · `_same_content`(find_..._for_user) · `create_note_for_user(user_id=...)` → 정상. 모든 조회 · 수정에 세션에서 꺼낸 user_id 조건. 노션 쪽은 그 사용자 토큰으로만 부르므로 남의 페이지 번호를 넣어도 404 → '찾지 못함'.
- 토큰 암호화 → token_crypto.py 전체, notion_service.py `_apply_tokens` · `_decrypt` → 정상. Fernet(AES-CBC + HMAC), 키는 환경변수만, 키 없음 · 형식 오류는 `TokenKeyError`(503), 못 풂은 `TokenDecryptError` → 끊김. 키 교체 미지원은 사용자 결정(D-021). 참고: 암호문이 user_id에 묶이지 않아(연관 데이터 없음) DB 쓰기 권한이 있는 공격자는 줄끼리 토큰을 바꿔 끼울 수 있으나, 그 권한이면 다른 데이터도 다 바꿀 수 있어 지적하지 않음.
- 토큰 노출(로그 · repr · 응답) → client.py `NotionTokens`(field repr=False, 70~78) · `_token_request` 로그(199: path · status · error 코드만) · `_api` 로그(266: 경로 첫 칸만), notion_service.py 로그(user_id · 예외 타입명만), api/notion.py 응답 모델(`NotionStatusOut`은 workspace_name만) → 정상. 프론트(lib/notion.ts · notion-status.ts · notion-data.ts)에도 토큰 칸 없음. 참고: callback 주소의 `code` · `state`가 접근 로그에 남을 수 있으나 code는 한 번만 쓰이고 교환에 client secret이 필요해 지적하지 않음.
- 갱신(교체 · 동시 갱신) → notion_service.py `NotionSession._refresh`(325~358) · `_locked_connection` · `call`(368~378) → 정상. FOR UPDATE로 잠근 뒤 "저장된 접근 토큰 ≠ 내가 쓴 토큰"이면 그 토큰을 씀 → 같은 옛 갱신 토큰으로 두 번 갱신하지 않음. 받은 쌍은 매번 `_apply_tokens`로 저장. 참고: 갱신 동안 줄 잠금을 쥐는 것은 1차에서 의도로 남김(D-021 '동시 갱신은 잠그고'), SQLite에서는 FOR UPDATE가 무시되나 운영 DB는 PostgreSQL.
- 갱신(끊김 기준) → `_refresh` except 분기(348~355) · `_mark_broken_if_current`(360~366) · `_decrypt`(290~298) → 정상. invalid_grant만 끊김(토큰 지움), invalid_client는 503(연결 유지), 그 밖은 502(연결 유지), 두 번째 401은 잠그고 그새 다시 연결했는지 본 뒤 끊김. D-021과 같음.
- 갱신(토큰 요청 재시도 안 함 · 시간 예산) → client.py `_token_request`(170~204: `retries=0`, `cut_timeout=False`, 남은 예산 < 15초면 보내지 않음) → 정상. 갱신 토큰이 바뀐 뒤 응답만 잃는 경우를 만들지 않음. 참고: 예산 부족(`NotionDeadlineError`)은 줄을 잠근 뒤에 판정돼 잠금이 요청 끝 `release_import`의 rollback까지 남지만, 그 뒤 노션 호출이 없어 길게 붙잡지 않음.
- 회수 → notion_service.py `disconnect`(201~216), client.py `revoke` → 정상. 복호화 → commit(트랜잭션 닫음) → 회수 시도 → 실패 · 키 오류여도 우리 쪽 줄 삭제(204). 참고 [추정]: ① 노션 `/oauth/revoke`에 접근 토큰을 보내면 갱신 토큰까지 무효가 되는지는 노션 문서로 확인 필요(우리 쪽은 둘 다 지우므로 노출 위험은 낮음). ② 끊기 도중 다른 요청이 갱신을 끝내면 새 토큰 쌍은 노션 쪽에서 회수되지 않고 우리 쪽에서만 지워짐(희귀한 겹침, 지적 아님).
- 입력 검증(페이지 · 블록 번호 → URL) → api/notion.py `NotionImportIn`(최대 20개 · 한 개 64자), notion_service.py `normalize_page_id(s)`(115~132: 32자리 16진수만 → 하이픈 UUID), `_fetch_tree`(583~591: 응답 블록 번호도 같은 검사 뒤 주소에), client.py `list_children`(start_cursor는 params로 인코딩) → 정상. 경로에 들어가는 값은 모두 UUID 형식뿐이라 경로 조작 불가. `kind`는 Literal.
