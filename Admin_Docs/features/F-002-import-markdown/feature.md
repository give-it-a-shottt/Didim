# F-002 기록 가져오기 — 마크다운 업로드와 처리

## 한눈에 보기 (코드 몰라도 OK)
상태: [됨] 1주차 기준. 4차 리뷰 [통과](2026-11-10), 최종 코드로 pytest 152개 SQLite · PostgreSQL 통과.
언제: 1주차 (읽기 · 나누기). '만들기'(퀴즈 · 카드 후보)는 3 · 4주차(F-004 · F-006)
무엇을: 마크다운 파일을 올리면 노트로 읽고, 제목 기준으로 조각을 나눠 저장해요. 결과는 노트 · 조각 · 중복 · 실패 개수로 요약해요.
왜: 마크다운으로 쓴 공부 기록이 이후 검색 · 퀴즈 · 카드의 재료이자 근거가 되게 하려고요.

## 설계 의도 (사용자 확인 — 코드 작성 전에 채움, 문장 정리사 사용)
- 이 기능이 해결하는 문제: 마크다운으로 쓴 공부 기록을 올리면 노트와 조각으로 저장해, 이후 검색 · 퀴즈 · 카드의 재료이자 근거가 되게 한다. (사용자 확인)
- 완료 기준(1주차): (사용자 확인)
  1. .md 파일을 올리면 파일마다 노트 1개 + 조각 여러 개로 저장된다. 노트 제목은 첫 `#` 제목, 없으면 파일 이름.
  2. 조각은 제목(`#` ~ `###`) 기준으로 나누고, 한 조각이 기준 길이(임시 1,500자)를 넘으면 문단 경계에서 다시 자른다.
  3. 같은 내용을 다시 올리면 저장하지 않고 '중복'으로 알려 준다.
  4. 일부 파일이 실패해도 성공한 파일은 저장하고, 실패한 파일은 이유와 함께 보여 준다.
  5. 결과 요약: 노트 N · 조각 M · 중복 K · 실패 F.
  6. 다른 사용자의 노트와 섞이지 않는다(D-004).
  7. '만들기'(퀴즈 · 카드 후보)는 3 · 4주차에 붙인다.
- 기록 종류: 1주차는 학습 노트 / 프로젝트 · 경험 중 사용자가 고른다(기본 학습 노트). '자동'은 AI 단계를 붙일 때 추가. (사용자 확인)
- 상한: 한 번에 20개, 파일당 1MB (상수로 두고 나중에 바꿀 수 있음). (사용자 확인)
- 처리 방식: 요청 한 번에 처리. '나갔다 와도 이어 보기'는 AI 단계를 붙일 때 만든다(Q-008은 그때 닫음). (사용자 확인)
- 화면 · 컴포넌트: IMP_01_001 올리기 · 003 결과 요약 · 900 오류 모달. 002 처리 중은 요청 동안 진행 표시만. 노션 탭은 '4주차' 비활성(D-001). (사용자 확인)
- API: `POST /api/notes/import` (파일 여러 개 + 기록 종류) → imported / duplicates / failed 목록. 401 로그인 안 함, 400 파일 없음, 413 전체 용량 초과. (사용자 확인)
- 데이터: notes(source=markdown) · chunks 그대로 + 조각에 제목 경로(예: `# React > ## useEffect`)와 원문 시작 · 끝 글자 위치를 추가 → 버전 파일 0002. (사용자 확인)
- R1 제안 2건(fix-01-alembic 2차)은 F-002 구현 때 같이 고친다. (사용자 확인)
- 1차 리뷰 뒤 추가(사용자 확인, 2026-11-10): 노트당 조각 2,000개를 넘으면 그 파일만 실패. 제목만 있는 파일(조각 0개)은 실패로 처리. 어댑터 인터페이스는 4주차 노션 때 만든다.
- 2차 리뷰 뒤 추가(사용자 확인, 2026-11-10): 제목 경로의 제목 한 단계는 200자까지만 저장하고, 넘으면 '…'을 붙인다.

## 면접 예상 질문
1. **질문 (AI 작성)**: 업로드한 마크다운을 조각으로 나눌 때 왜 제목 기준 + 길이 기준을 같이 썼고, 조각에 제목 경로와 원문 위치(시작 · 끝)를 따로 저장한 이유는 무엇인가요? "조각 내용 == 원문[시작:끝]" 규칙은 어떻게 지켰나요?
   - 답 (사용자 확인 — AI 초안을 외워 설명, 2026-11-10):
     - 공부 노트는 보통 제목 하나에 주제 하나라서, 제목(`#` ~ `###`)으로 자르면 조각이 의미 단위가 돼요. 검색 · 퀴즈의 근거로 쓰기 좋아요. `####`부터는 너무 잘게 쪼개져서 안 나누고, 코드 블록 안의 `#`은 제목으로 보지 않아요.
     - 그런데 제목 하나 아래 글이 아주 길면 검색이 흐려지고 LLM에 보내는 양도 커져요(설계 원칙 6). 그래서 1,500자를 넘으면 문단 → 줄 → 글자 순서로, 되도록 자연스러운 경계에서 다시 잘라요.
     - 조각만 떼어 놓으면 "이게 어디 얘기인지"를 잃어요. 그래서 `# React > ## useEffect` 같은 제목 경로를 같이 저장해 화면에 출처로 보여 주고, 나중에 검색 문맥으로도 써요. 리뷰에서 제목 경로가 끝없이 커질 수 있다는 지적이 나와서 한 단계 200자까지만 저장해요.
     - 원문 위치(시작 · 끝)는 근거 우선(D-003) 때문이에요. AI가 만든 퀴즈나 문장이 "원문의 정확히 어디"에서 나왔는지 가리키려면 위치가 있어야 해요.
     - 규칙은 구조로 지켰어요. 나누기는 글을 복사하거나 고치지 않고 위치만 계산하고, 조각 내용은 원문을 그 위치로 잘라 낸 것이에요. 그리고 저장 직전에 한 번 더 "조각 내용 == 원문[시작:끝]"을 검사해서, 다르면 그 파일만 실패시키고 아무것도 저장하지 않아요(`ChunkLocationError`). 줄바꿈은 먼저 `\n`으로 통일해서 CRLF 파일도 위치가 맞아요.
     - 한계: 위치는 파이썬 글자 단위라, 화면(자바스크립트, UTF-16)에서 이모지가 든 글을 짚으려면 변환이 필요해요.
2. **질문 (AI 작성)**: 파일 업로드 API에서 "너무 큰 요청"을 어디서, 어떤 순서로 막았나요? FastAPI가 엔드포인트보다 먼저 본문을 읽는다는 점과, 리뷰에서 나온 주소 끝 줄바꿈(`%0A`) 우회는 어떻게 다뤘나요?
   - 답 (사용자 확인 — AI 초안을 외워 설명, 2026-11-10):
     - 세 겹으로 막았어요. 화면 → 미들웨어 → 엔드포인트 순서예요.
     - FastAPI는 업로드 폼을 끝까지 받아 임시 파일에 쓴 다음에야 로그인 확인(의존성)과 엔드포인트를 불러요. 그래서 엔드포인트에서 크기를 보면 이미 다 받은 뒤예요. 1차 리뷰에서 크기 머리말 없이(chunked) 보내면 로그인도 안 한 요청 하나가 메모리를 약 1GB까지 쓰게 할 수 있다는 게 나왔어요.
     - 그래서 그보다 앞에서 도는 ASGI 미들웨어(`ImportUploadGuard`)를 만들었어요. 본문을 받기 전에 ① 세션 쿠키가 없거나 서명 · 만료가 틀리면 401 ② 크기 머리말(Content-Length)이 21MB를 넘으면 413 ③ 머리말이 없거나 거짓이면 실제로 받은 바이트를 세다가 넘는 순간 413으로 끊어요.
     - 엔드포인트는 그 뒤에 파일 20개 · 파일당 1MB · 합계 20MB를 다시 확인해요. 화면도 보내기 전에 개수 · 합계를 먼저 막는데, Next.js 프록시가 서버가 일찍 보낸 413을 연결 끊김으로 바꿔 버려서 사용자가 이유를 못 보기 때문이에요(T-004).
     - `%0A` 우회: 라우터는 경로 끝의 줄바꿈을 무시해서 `/api/notes/import\n`도 가져오기로 들어가는데, 가드는 경로를 정확히 비교해서 그 주소면 검사를 건너뛰었어요. 그래서 가드가 모든 요청에서 경로에 줄바꿈 같은 제어 문자가 있으면 본문을 읽기 전에 400으로 막게 했고, 경로도 라우터와 같은 기준(root_path를 뗀 경로)으로 비교해요. 이 우회는 테스트로 고정했어요.
3. **질문 (AI 작성)**: 리뷰에서 제목 정규식이 공백이 긴 줄에서 느려지는 문제(ReDoS)와, 줄이 아주 많은 파일이 메모리를 180MB 쓰는 문제가 나왔습니다. 원인은 무엇이었고, 어떻게 측정하고 고쳤나요?
   - 답 (사용자 확인 — AI 초안을 외워 설명, 2026-11-10):
     - ReDoS 원인: 제목 정규식에 같은 공백을 여러 갈래가 나눠 먹을 수 있는 겹치는 반복이 있었어요. 매칭이 실패하면 정규식이 나누는 방법을 전부 되돌아가며 시도해서, 공백이 길수록 시간이 제곱으로 늘어요.
     - 측정: 공백 4,000개 0.09초 → 8,000개 0.36초. 길이가 2배일 때 시간이 4배라 제곱이에요. 1MB 한 줄이면 약 1.5시간으로 추정됐고, 그동안 서버 전체가 멈춰요.
     - 고침: 겹치는 반복을 없애고, 닫는 `#`과 끝 공백은 정규식 대신 문자열 처리로 떼었어요. 코드 블록 닫는 줄도 따로 검사해요. 긴 공백 줄의 처리 시간을 테스트로 고정했어요.
     - 메모리 원인: 한 구역에 줄이 100만 개쯤 있는 1MB 파일에서 약 180MB를 썼어요. 구역의 모든 줄을 줄 객체 목록으로 쌓고, 긴 구역은 문단 · 단위로 나눌 때 목록을 또 만들었기 때문이에요. 글은 1MB인데 줄마다 붙는 객체 비용이 훨씬 컸어요.
     - 고침: 구역을 줄 목록 대신 위치(시작 · 끝)로만 흘려보내고, 1,500자를 넘는 구역만 그 구간을 다시 훑어요. 줄 읽기도 `str.find`로 한 줄씩 해요. 180MB → 2~3MB로 줄었고, `tracemalloc`으로 최대 메모리를 재는 테스트로 고정했어요.
