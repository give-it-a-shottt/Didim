# D-011 화면은 뼈대 먼저, 각 화면은 주차별로 완성한다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과] 사용자가 골랐어요(2026-11-08).
무엇을: 먼저 1~2일 동안 공통 레이아웃(왼쪽 메뉴 등)과 화면 주소(라우트) 32개를 빈 화면으로 만들어요. 그다음에는 매주 그 주 기능의 화면을 피그마대로 완성하면서 서버를 같이 붙여요. 집으로 치면 방 배치와 문부터 다 달고, 인테리어는 이사 들어갈 방부터 하는 거예요.
왜: 전체 지도(라우팅)를 처음에 확정하면서도, 핵심인 서버 · AI("지어낸 문장을 잡아내는 설계")에 쓸 시간을 지키려고요. 화면과 API를 같이 만들면 데이터를 붙일 때 화면을 다시 고칠 일이 줄어요.

## 개발자 상세

### 상황
- 피그마에 화면 30개가 그려져 있고, 사용자는 화면을 먼저 다 만들고 기능을 붙이는 방식을 검토했어요(Q-011).
- 8주 MVP라 시간이 정해져 있고, 프로젝트의 증명 목표는 평가 수치(D-005)예요.

### 후보
| | A. 화면 30개 먼저 다 | B. 뼈대 먼저, 화면은 주차별 | C. 기능마다 화면 + 서버 |
|---|---|---|---|
| 장점 | 피그마가 생생할 때 옮김, 전체를 클릭해 볼 수 있음 | 라우팅이 처음에 확정, 화면 · API를 같이 만들어 재작업이 적음 | 가장 단순 |
| 단점 | 화면에 2주 이상 들 수 있어(추정) 핵심이 늦어짐, API 모양을 모르고 만든 화면은 다시 고쳐야 함 | 빈 화면이 한동안 남음 | 전체 흐름이 늦게 보임 |

### 결정
- B. 1단계: 공통 레이아웃 + `didim-design.md` IA v2의 1차 화면 전부를 라우트로 만들고 각 화면은 제목만 둔다. 화면 ID ↔ URL 대응은 [screens.md](../overview/screens.md)에 적는다.
- 2단계부터: 주차별 기능(F-00X)을 할 때 그 화면을 완성하고 API를 붙인다.

### 결과로 생기는 제약
- 뼈대 단계의 빈 화면은 기능이 아니라서 STATUS의 기능 상태를 올리지 않는다.
- 뼈대 단계는 라우팅 코드만 바뀌므로 R4(screens.md ↔ 라우팅) 위주로 본다. 화면 모양은 리뷰하지 않는다.
- 2차 화면(Cmd+K 검색, 칸반)은 라우트도 만들지 않는다(D-006).

### 이 결정을 바꿔야 하는 조건
- 서버 · AI 쪽이 일정보다 크게 앞서서 화면이 병목이 되면, 남은 화면을 한꺼번에 완성하는 쪽(A)으로 바꿀 수 있다.
