## 지적 (있을 때)
- [신규] [주의] [확실] 테스트 ①이 "끝 신호(onTransitionEnd)가 동작한다"를 증명하지 못한다. 끝 신호가 고장 나도(예: propertyName 조건이 틀려도) 안전 타이머(200+100ms)가 같은 최종 상태(data-state=short, line-clamp-4)로 만들고, toHaveAttribute의 기본 대기(5초)가 300ms보다 길어 그대로 통과한다. ③은 끝 신호 없이 타이머만, ④는 전환 없음만 본다. 그래서 끝 신호 갈래(`event.propertyName === "max-height" && !expanded`)를 지켜 주는 단계가 없다 — posting-aside.tsx 201~203줄, applications.spec.ts 182~187줄 — 확인한 범위: 두 파일의 해당 줄 전부 — 고치는 방법: 끝 신호가 먼저 오는지 가른다. 접기 전에 body에 inline `transitionDuration`을 길게(예: "2s") 줘서 타이머를 2.1초로 늘리고, 접은 뒤 1초 안에 short가 되는지 보거나(타이머 전에 끝나면 끝 신호 덕), 전환을 끈 상태에서 `new TransitionEvent("transitionend", {propertyName:"max-height", bubbles:true})`를 보내 100ms 안에 short가 되는지 + `propertyName:"opacity"`는 무시되는지 확인.
- [신규] [제안] [확실] 시간에 기대는 단언이 느린 환경에서 깨질 수 있다. ①의 click 직후 `state()==="full"`은 전환 200ms가 끝나기 전에 읽는다는 가정, ③의 `waitForTimeout(100)` 뒤 `full`은 click부터 읽기까지 300ms(타이머) 안에 끝난다는 가정이다. CI가 느려 evaluate 두 번이 200ms 넘게 걸리면 위양성 실패가 난다(8회 통과는 이 가정이 로컬에서 맞았다는 뜻일 뿐). 200 · 100 · 400 숫자는 CSS 토큰(--motion-duration) 값에 암묵적으로 묶여 있어 토큰이 바뀌면 ②가 말없이 무의미해진다 — applications.spec.ts 184·193·209·210줄 — 확인한 범위: 해당 줄 — 고치는 방법: 테스트 시작에 body의 inline `transitionDuration`을 "1s" 등 크게 고정하고 대기 시간을 거기서 계산해(읽어서) 쓴다. 숫자 상수를 지우고 창을 넓힌다.
- [신규] [제안] [확실] "펼치는 중에 접기"(11차에서 찾은 버그 2의 실제 경로)를 실제 전환으로 검증하는 단계가 없다. ②는 열기→접기→열기로 끝나 최종 full만 보고, ③은 전환을 끈 채 취소 신호를 흉내 낸 것이라 브라우저가 실제로 보내는 transitioncancel 흐름이 아니다. 또 ②의 세 번 클릭이 200ms 안에 끝났다는 보장이 없어(느리면 접기가 먼저 끝나고 다시 펼침) 의도한 경로를 안 거치고도 통과한다 — applications.spec.ts 189~195줄 — 확인한 범위: 해당 줄 — 고치는 방법: 전환을 길게(위와 같이 inline) 늘린 뒤 "열기 클릭 → 곧바로 접기 클릭" 직후 `state()`가 full인지(버그 2 재현 조건: 바로 short가 되면 실패), 그 뒤 결국 short가 되는지 단언.
- [신규] [제안] [추정] "화면을 떠남" 경로(`useEffect(() => clearFallback, [])`)를 확인하는 테스트가 없다. 코드상 타이머를 정리하고, 정리를 빠뜨려도 React 19에서는 언마운트된 컴포넌트의 setState가 경고 없이 무시되므로 실제 해는 작다 — posting-aside.tsx 158줄 — 확인한 범위: 코드와 테스트 전체 — 확실해지는 방법: 접는 도중 다른 페이지로 이동한 뒤 콘솔 오류가 없는지 보는 테스트 한 줄(`page.on("pageerror")`). 안 해도 된다.
