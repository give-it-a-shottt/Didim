## 지적
- [신규] [제안] [추정] 출처 확인이 머리말 없는 요청을 받는 구조(fail-open)라 두 경우에 조용히 꺼진다. ① Sec-Fetch-Site를 안 보내는 브라우저(예: Safari 16.4 미만)의 다른 사이트 form POST는 통과. ② 배포 때 앞단 프록시 · CDN이 `Sec-*` 머리말을 빼면 모든 요청이 '머리말 없음'이 되어 검사가 통째로 꺼지고 테스트로 알 수 없다. 영향은 몰래 로그아웃 · 읽기 전용 샘플 세션으로 바꿔 끼우기 정도라 낮다. — `backend/app/api/deps.py` reject_cross_site — 확인한 범위: 패킷 diff, test_logout_refuses_cross_site_requests, 패킷의 Next 프록시 확인(로컬 next start만, 실제 배포 경로는 못 봄) — 고치는 방법: Sec-Fetch-Site가 없을 때만 Origin을 본다 — Origin이 있는데 허용한 사이트 주소(설정값)와 다르면 403, Origin도 없으면(curl · 테스트) 지금처럼 받기. 배포 문서에 '이 두 주소는 화면과 같은 출처(Next 프록시)로만 부르고, 프록시가 Sec-Fetch-Site · Origin을 넘겨야 한다' 한 줄.

## 체크 항목별 근거
- 로그인 CSRF(로그아웃 · 체험 열기) → reject_cross_site가 경로 의존성이라 핸들러보다 먼저 돎. 403이면 set-cookie 없음(테스트). 허용은 same-origin · none뿐, same-site도 거절(서브도메인 탈취에도 막힘). `.lower()` 비교 · `Cross-Site` 테스트로 대소문자 확인. none은 사용자가 직접 연 요청에만 붙어 다른 사이트 form으로 못 만듦. 세션 쿠키가 Lax여도 다른 사이트에서 최상위로 연 POST의 응답이 쿠키를 지우거나 심는 건 못 막으므로 이 두 경로에 머리말 검사가 맞는 통제 → 적절(머리말 없을 때 정책만 제안).
- Next 프록시 경유 → 화면은 같은 주소의 /api/*를 fetch로 불러 same-origin, 패킷의 curl 확인으로 rewrites가 머리말을 FastAPI까지 넘김. 백엔드를 다른 서브도메인에서 직접 부르게 바꾸면 정상 요청이 same-site가 되어 403 — 배포 문서에 남길 사항(제안에 포함) → 적절.
- 다른 쿠키 바꾸는 경로 → 머리말 검사가 필요한 POST는 ALLOWED_WRITES의 둘(로그아웃 · 샘플 세션)뿐이고 둘 다 붙음. 다른 쓰기 API는 Lax 쿠키라 다른 사이트 POST에 쿠키가 안 실림. 구글 · 노션 콜백은 GET + OAuth state 쿠키로 보이나 [추정](패킷 밖) → 이번 범위에 남은 문제 없음.
- 리포트 새 칸(display · data_items) → display는 서버 상수 규칙으로 만든 글자라 새 정보 없음. data_items는 공개하던 data를 DATA_LABELS 키로만 거른 것이라 범위가 더 좁음. with_display가 원본 칸(result_file · dirty 등)을 들고 가지만 응답 모델 기본값(extra 무시)과 response_model이 걸러 나가지 않음(report.py 확인). 가상 데이터라 개인 기록 없음(D-005) → 문제없음.
- 화면 XSS → display · dataSizeText는 JSX 텍스트로 이스케이프, dangerouslySetInnerHTML 없음. 모양이 틀리면 전체 '못 읽음'(D-030) → 문제없음.
- 입력 검증 · 에러 노출 → is_integer()는 inf · nan에서 False라 int() 오버플로 없음. 모양이 틀린 칸은 고치지 않고 넘겨 검사 모델이 그 회차만 뺌(테스트 있음). EvalOut.error 노출은 전부터 있던 것 → 문제없음.
- 비밀값 · 민감 정보 → diff · eval_readme.py에 키 · 비밀번호 · 접속 정보 없음, 새 패키지 없음 → 문제없음.
- 성능(with_display) → 회차마다 얕은 사본 + 평가 × 수치(수십 칸) 한 번씩, list_summaries(파일 읽기)보다 훨씬 가벼움, DB 안 봄. 요청마다 파일을 읽는 건 D-030대로 → 문제없음.
- 성능(시드 리팩터링) → 쿼리 수 · 순서 같음, 오프라인 스크립트 → 문제없음.
- 성능(화면) → 새 fetch 없음, 함수 삭제로 번들이 조금 줄어듦, 서버 컴포넌트 → 문제없음.
