- [신규] [주의] [확실] 조각 상한으로 멈추는 것은 "조각 수"뿐이라, 한 구역(제목 사이)에 줄이 아주 많은 1MB 파일은 상한 안에서 정상 저장되면서도 파일 하나에 약 180MB 메모리와 2초 넘는 CPU를 쓴다. `_sections`가 구역의 모든 줄을 `MarkdownLine` 객체로 `current.lines`에 쌓고(chunking.py:67-69), 큰 구역이면 `_paragraphs` · `_units`가 줄마다 목록 · 튜플을 또 만든다(:82-111). 실측(레포 venv, `read_markdown_file` + `split_markdown(max_chunks=2000)`): `"a" + "\n" × (1MB-1)` → 조각 1개로 성공, 읽기 0.90초 + 나누기 1.24초, 나누기 최대 메모리 184MB / `"a\n\n" × 34.9만` → 조각 700개 성공, 0.60초 + 1.11초, 193MB / `"a\n" × 52만` · 코드 블록 안 52만 줄 → 조각 700개 성공, 약 1.1초, 125MB / 구역 2,000개 뒤에 큰 구역 하나 → `TooManyChunksError`지만 1.2초 · 127MB(넘는 조각이 마지막 큰 구역에서 나오면 일찍 멈춤이 도움이 안 됨). 원문 1MB 대비 약 180배. 요청 하나에 이런 파일 20개면 차례로 처리하므로 메모리는 파일 하나 몫씩 풀리지만 CPU는 약 40초(1개 측정값으로 외삽), 동시 요청이면 메모리가 요청 수만큼 늘어난다. 로그인한 사용자만 가능. 2차 지적 2(상한을 다 나눈 뒤 확인)와는 원인이 다름(구역 안 줄 수는 상한이 막지 않음). — 위치: backend/app/services/chunking.py:56-70, :82-111, :144-155, backend/app/importers/markdown.py:53, :84 — 확인한 범위: scratchpad 스크립트(r2_round3_split.py)로 함수만 실행해 시간 · tracemalloc 최대 메모리 측정. `MarkdownLine`에 `slots=True`만 주면 100만 개 기준 168MB → 130MB로 줄어드는 정도(별도 실측)라 그것만으로는 부족함. 20개 요청 시간 · 동시 요청 메모리는 외삽, 실제 서버로 재지는 않음. 파일 상한(1MB) · 조각 상한(2,000)은 사용자 결정이라 보지 않음. — 고치는 방법: 구역을 줄 목록 대신 위치로 들고 다닌다 — `_sections`가 (경로, 첫 줄 시작, 마지막 줄 끝, 본문 있음 여부)만 내보내게 하고, 기준 길이(1,500자)를 넘는 구역만 그 구간을 줄 단위로 다시 훑되 `_paragraphs` · `_units` · `_pack`을 제너레이터로 이어 붙여 조각이 나오는 대로 내보낸다(메모리가 줄 수가 아니라 조각 수에 비례). `find_title`도 1단계 제목이 없으면 `MarkdownLine`을 100만 개 만들며 끝까지 훑으니(0.9초), 같은 줄 읽기를 객체 없이(위치 · 글만) 돌게 하면 함께 줄어든다. 테스트: `"a" + "\n" × (1MB-1)`의 나누기 최대 메모리가 정해 둔 값(예: 30MB) 이하이고 시간이 0.5초 안인지.
