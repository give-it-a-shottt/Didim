## 체크 항목별 근거
- 프론트 로딩 · 에러 · 빈 상태 → 랜딩 `HeroMetrics`는 `null`이면 수치 칸만 숨고 링크는 Suspense 밖이라 남음. `/report` `ReportBody`는 `null`이면 `role=alert`, 빈 목록이면 `role=status` → 새 e2e 2개가 에러 · 숨김 경로를 직접 확인 → 충족.
- 백엔드 · 외부 API 실패 대응 → `fetchBackendPublic`은 fetch 예외 · `!response.ok` · JSON 파싱 실패를 모두 `null`로 → 충족. 백엔드 앱 코드 변경 없음.
- 테스트 정상 / 예외 균형 → 새 파일은 예외 경로, 정상 경로는 기존 landing.spec · report.spec(11 통과) → 충족.
- 테스트 통과 → tsc · eslint 통과, 전체 115 통과(113 + 새 2) → 충족.
- 우연히 통과할 가능성 → 위 제안 1. 스트리밍: `page.goto`는 load까지 기다리고 본문이 끝나야 load가 끝나므로 '기다림 글 0' · `definition` 0이 스트리밍 도중의 거짓 통과가 되기 어려움. '기다림 글 0'은 글이 한 번도 안 나와도 통과하는 약한 단언이지만 목적이 흔들림 방지라 문제 없음.
- 두 번째 `next start`가 같은 `.next`를 씀 → webServer는 순서대로 뜨고(패킷 확인), 두 번째의 URL 대기가 빌드 뒤에 풀려서 세 번째는 빌드 중인 `.next`를 읽지 않음. 리포트 · 랜딩 fetch가 `no-store`라 `.next/cache`에 쓸 일이 거의 없음(직접 확인 못 함). `BACKEND_URL`은 런타임 값이라 빌드 때 굳지 않음 → 위험 낮음. 순서를 바꾸면 깨지므로 config 주석이 경고 역할.
- 포트 충돌 → 3101 · 8101은 env로 바꿀 수 있고 helpers.ts가 config · spec에 같은 값을 줌. 8101이 점유돼 있으면 가짜 백엔드 전체가 죽고 `/api/health` 대기가 실패, 3101이 점유돼 있어도 `reuseExistingServer: false`라 눈에 띄게 실패 → 조용히 틀리지 않으므로 허용.
- config가 `./tests/helpers`를 가져옴 → helpers.ts는 `@playwright/test` 타입만 씀 → 문제 없음. 새 파일은 로그인하지 않아 포트 사이 쿠키 영향 없음.

확인한 범위: 리뷰 패킷 전체, `playwright.config.ts`, `src/lib/backend.ts`의 `BACKEND_URL` 줄, 포트 상수가 쓰인 곳 grep. 테스트 재실행 안 함, 파일 수정 안 함.
