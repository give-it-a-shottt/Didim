## 체크 항목별 근거
- 설계 의도 완료 기준 · 의도에 없는 기능
  - 기준 1(원문 위치): 1차 지적 1은 사용자 판정 "링크로 강조하면 충족"이고, feature.md:51에 "숫자 표시 안 함, 사용자 확인"이 적혀 해결됨. records.ts의 SearchResult가 start/end를 여전히 읽지 않는 것은 그 판정과 일치.
  - 기준 4(검색 로그): 시간 초과 · 검색 불가는 search_records에서 searcher.search가 먼저 예외를 던져 _save_log에 닿지 않으므로 로그가 안 남음(search_service.py 흐름, test_search.py의 `..._is_not_logged`). api-list의 "로그 안 남김"과 일치.
  - 의도에 없는 기능: 3초 시간 상한(503)과 btree_gin 합친 색인은 사용자가 정한 것(패킷 · feature.md:40-41에 사용자 확인 명시). 사용자 선택이 질문 없이 들어간 경우에 해당하지 않음. 새 기능 추가 없음.
- api-list ↔ 프론트 ↔ 백엔드 3자 비교(바뀐 응답만)
  - `GET /api/search` 503: 백엔드 search.py가 SearchUnavailableError → UNAVAILABLE_DETAIL, SearchTimeoutError → TIMEOUT_DETAIL로 모두 503 `{detail}`. api-list "503 이 DB에서 검색 불가(SQLite) · 3초 시간 상한 초과(detail에 이유, 화면이 그대로 보여 줌, 로그 안 남김)"와 일치. 프론트 records.ts:90-94가 503이면 body.detail(문자열일 때)을 message로 쓰고 없으면 기본 문구, records/page.tsx:73이 그 message를 그대로 표시 → 문서 · 코드 · 화면 일치. 503 외 오류(400 · 401 · 422 · 500)는 "error"로 묶임(401은 사용자 판정으로 고치지 않음).
  - `GET /api/notes/{note_id}` 404 범위: 백엔드 notes.py:87-88이 1~MAX_NOTE_ID(2,147,483,647) 밖이면 DB 조회 없이 404 + 같은 detail. api-list의 "번호가 1~2,147,483,647 밖 404"와 일치. 프론트 `parseDbId`(page.tsx:16-22, 1~10자리 · 같은 상한)는 범위 밖을 서버를 부르기 전에 notFound()로 막고, 서버가 404를 줘도 getNote가 not-found로 처리 → 같은 결과. 422(숫자 아님)는 프론트가 먼저 404로 막아 도달하지 않음. 상한값은 백엔드 · 프론트 · api-list 세 곳에 따로 적혀 있으나 값이 모두 같음.
  - 응답 필드 · 타입(NoteDetailOut · NoteChunkOut · SearchResponse)은 1차 이후 변경 없음, 문서 = 백엔드 = 프론트 읽는 필드 일치 유지.
- 1차 지적 해결 여부
  - 지적 1(원문 위치 숫자): 사용자 판정 "링크 강조로 충족", feature.md:51에 반영 → 해결.
  - 지적 2(401 구분): 사용자 판정 "고치지 않음"(회원 레이아웃이 먼저 거름) → 의도된 보류, 재지적 안 함.
  - 지적 3(큰 노트 ID): 프론트 parseDbId + 백엔드 MAX_NOTE_ID 이중 방어, 테스트(0 · -1 · 2^31 · 10^20 → 404)와 api-list 갱신 → 해결.
- screens.md 라우트 ↔ 라우팅 코드: 이번에 라우트 변경 없음(파일 경로 · 쿼리 이름 `?q=` · `?chunk=` 그대로). `?chunk=`가 배열로 오는 경우도 parseDbId가 typeof 검사로 null 처리.
